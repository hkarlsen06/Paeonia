# Implementation Map

This is the first stop when an agent needs to find the current owner of a Paeonia behavior. Keep this file to ownership: which file owns what, the names users see mapped to code names, and constraints the code does not show. Durable rules belong in `AGENTS.md`.

## Launch, root state, and navigation

- `ios/PaeoniaApp/App/RootView.swift`: root body, root banner mounting, and the cold-launch intro (`LaunchExperienceView`), which stays up until the intro signals it has fully unmasked the app, not when `state` leaves `.launching`. `RootView+Screens.swift` maps each `AppState` to one screen and puts profile setup, the paywall, pairing, joining and the account notices in `PaeoniaScreenFrame` (`Shared/DesignSystem/Components/PaeoniaScreenFrame.swift`), so only their content crossfades. Profile setup, the unpaired paywall, joining and the invite screen pass the frame a `progress`, and it shows the onboarding progress bar above them. `RootView+Actions.swift` forwards user actions and reacts to session, state and invite-code changes (an invite link opened while paired is dropped with a banner). `RootView+System.swift` owns deep links, widget sync, push registration and the foreground pass (one at a time, refreshing location next to the sync so content never waits on GPS). `RootView+PermissionPrimers.swift` asks for nothing when the app opens: primers wait until the person has answered a question or sent a drawing (`MainTabActions.sentSomethingToPartner`), the notification primer comes first, and at most one shows per visit.
- `ios/PaeoniaApp/App/PaeoniaApp.swift`: builds `RootViewModel` and `LocationMapViewModel` once, after Clerk is configured, and gives the root view model a Clerk session check so a session that ends while the app runs is noticed.
- `ios/PaeoniaApp/Features/Auth/LaunchExperienceView.swift`: the cold-launch overlay. It looks exactly like the system launch screen and holds until `contentReady`, then fades out over the first app surface. Nothing in it moves, so the fade can overlap the system launch screen's own fade or the app lock's cover, which show the same mark, without showing two marks. `LaunchScreenCanvas.swift` draws `LaunchBackground` and `PaeoniaLaunchPetalMark` as `UILaunchScreen` in Info.plist does and fades them with Core Animation, because the first surface builds in the update that starts the fade and a SwiftUI animation would lose part of it. Without the mark it draws the plain background, and the answer flow fades it as a curtain when it opens in place (`DailyFlowCurtainView`).
- `ios/PaeoniaApp/Features/Auth/LaunchReveal.swift`: glue between the overlay and the surface it uncovers. `EnvironmentValues.launchContentRevealed` flips true as the overlay starts to fade, and `launchIntroComplete` once it has faded and the Home map's intro flight has landed. `RootView` sets both on the routed content, and both default to `true` outside the cold launch. `launchOverlayShowing` is true until the overlay has faded. `RootView+Screens.swift` gives it to the tabs, so today's question can open under a copy of the launch screen. The map reports its flight through `LaunchMapFlight`. Compact-width Home uses `HomeMapLayout`, whose map intro also waits for the app to be active, so it does not play under the App Store purchase sheet or a system alert. The regular-width `CoupleMapCard` flame sweep waits on `launchContentRevealed`. The file also has reusable entrance modifiers.
- `ios/PaeoniaApp/Features/Auth/AuthBaselineViews.swift`: `AuthLaunchingView`, the copy-free loading surface under the cold-launch intro, plus the deleting-account and relationship-ended screens. Scenarios `onboarding-usage`, `relationship-ended`, `account-closed` and `deleting-account` open the single-purpose screens after sign-in in their frame.
- `ios/PaeoniaApp/Features/Auth/Onboarding/AuthOnboardingView.swift`: profile setup after the first sign-in (a name and a cropped photo, both required; an imported Google photo counts). `AuthOnboardingPhotoField.swift` is the photo picker, and `AuthOnboardingPhotoNudge` counts taps on a missing photo. The start date is asked before sign-in (`Welcome/WelcomeStartDateStep.swift`).
- `ios/PaeoniaApp/Features/Auth/Welcome/`: the signed-out flow. `WelcomeFlowModel.swift` is the state machine (`WelcomeStep`: welcome, start date, drawing, sign-in with a `WelcomeSignInMode` of start, joining or returning). `WelcomeFlowView.swift` crossfades the steps. Only the welcome screen shows the logo, and every later step sits in `PaeoniaScreenFrame`, the frame the post-sign-in screens use.
  - `WelcomeView.swift` is the first screen, with `PaeoniaWordmark`, the doodle (`WelcomeWidgetDoodle.swift`, strokes in `WelcomeDoodleInk.swift`, touch drawing in `WelcomeFingerDoodle.swift`) and three buttons: "Start our space", "I was invited" and "I already have an account". "I was invited" opens `PairingCodeEntrySheet`. When the clipboard holds a link, which the `/join` web page copies before sending a partner to the App Store, that row becomes a system Paste button. A pasted join link saves its code and anything else opens the code sheet. A saved code (from there, a link, or the sign-in step's Change code) moves to sign-in for joining, and the join screen opens for it after profile setup.
  - Start path: `WelcomeStartDateStep.swift` (the date and `RelationshipDaysReveal`). The date waits in `WelcomeFlowStore.swift` and goes into the outbox as `FirstDayStartedOnQueue`, kind `setFirstDayStartedOn`, when `RootView+Actions.sessionChanged` sees a session. Then `WelcomeDrawingStep.swift`, the real `WidgetDrawingView` with no owner, couple or live relay, and `WelcomeDrawingUploader.swift`, whose send only marks the saved drawing `isFirstDay`. The drawing then lands on `WidgetHomeScreenMock`.
  - The welcome doodle carries into the first drawing: it waits in `WelcomeFlowStore` as `carriedDoodle` and `WidgetDrawingViewModel.addStrokesOnceLoaded` puts it on the draft once the canvas has loaded. Every other way out of the welcome screen drops it.
  - Before sign-in the drawing and its marker live in `WelcomeDrawingStorage.swift` (a canvas in `Application Support/WelcomeDrawing` and a marker under its own key), apart from the widget's, so another account's data left on the phone (`RootDeviceOwnerStore`) never shows on the canvas and clearing it at sign-in (`RootViewModel.clearDataFromAnotherAccount`) never reaches the drawing. After that clearing, `WelcomeFlowModel.sessionStarted` moves the drawing to `WidgetCanvasService.shared` with the `isFirstDay` marker in `WidgetPendingUploadStore.shared`, and the invite screen sends it (`InviterFirstDayModel.load`). Choosing to join or to sign in to an existing account drops it.
  - `WelcomeSignInStep.swift` has `WelcomeSignInPicture` (the waiting first drawing, rendered by `WelcomeFlowModel.waitingDrawingImage`, or else `WelcomeHero` from the `Welcome` asset folder), the Apple, Google and email buttons and the in-app privacy, terms and support links. Only the tapped provider shows a spinner (`RootViewModel.signingInWith`). The email button opens `EmailSignInSheet.swift`: the address, then the 6-digit code Clerk emails, with the error under the field instead of a banner. `RootViewModel.sendEmailSignInCode` and `signInWithEmailCode` return an `EmailSignInError` for the sheet. `LiveAuthGateway.sendEmailCode` starts a Clerk sign-in, or a sign-up for a new address, and keeps the attempt until the code is entered. An instance that skips email verification at sign-up (the development one) gets signed out and sent a sign-in code, so every new address proves itself with a code. `testEmailCodeSignInReachesProfileSetup` in `PaeoniaAppUITests` drives it in `local-flow-fresh`, where any code signs in. Someone who signed in on this phone before opens at sign-in for returning.
  - `WelcomeFunnelRecorder.swift` counts how many installs reach each step (`backend/convex/onboarding.ts`): once per step per install, the step name only, no auth header, not PostHog.
  - Scenarios `welcome`, `sign-in`, `sign-in-invite`, `welcome-start-date`, and `local-flow-fresh` for the whole journey.
- `ios/PaeoniaApp/App/RootViewModel.swift`: root auth, access and pairing state. `RootRoute.swift` is the route enum, and the selected tab resets to Home whenever the state leaves `.paired`. `RootViewModel+Account.swift` owns sign-in, sign-out, deletion, profile saves, and sessions that end on their own (back to sign-in with a banner, local data kept). `RootDeviceOwnerStore.swift` remembers whose data is on the phone, so signing in as someone else clears it like a sign-out. `RootViewModel+Launch.swift` is the cold launch: `PaeoniaApp.init` calls `beginLaunch()`, which starts the session restore (`ClerkAuthService.restoreSession`, one `identity:launch` call returning the profile and the access snapshot) and reads the saved state before the scene exists, and `start()` awaits them. `showSavedLaunchPreview()` opens Home on the first frame from the saved session and a saved paired snapshot, only when the phone holds this account's data and no privacy purge is pending. It commits nothing, purges nothing and celebrates nothing, and the launch result settles it. `RootViewModel+AccessResolution.swift` resolves access, `+Sync` starts sync (and stops if the session ended during startup), `+Refresh` re-checks access after a purchase, a renewal or a pairing change without restoring the session (so a failed check never signs anyone out), and `+State` holds the read-only state the views use. `RootPairingCelebrationState.swift` decides when the celebration and the first day sequence show. Tests: `ios/PaeoniaAppTests/RootViewModelFlowTests.swift`, `RootViewModelLaunchTests.swift`, `RootSessionLifecycleTests.swift`.
- `ios/PaeoniaApp/Features/AppLock/`: the optional Face ID, Touch ID or passcode lock, off by default and stored on the phone only (`UserDefaultsAppLockStore`, keys `paeonia.appLock.*`). The sign-out and account deletion purge clears it (`LocalPrivacyPurgeService` calls `AppLockModel.shared.reset()`). `AppLockModel` decides the state and `AppLockPolicy` the grace period. `AppLockCoverController` puts `AppLockCoverView` in its own `UIWindow` above everything, including sheets, and feeds the model the `UIScene` activate, deactivate and background notifications synchronously. `LocalAuthenticationAppLockAuthenticator` uses `.deviceOwnerAuthentication`, so the passcode is always the fallback. `AppLockRootModifier` is mounted on the routed content in `RootView+Screens.swift`. While locked, `RootView+System.swift` holds deep links and notification taps (`isHeldByAppLock`, `deepLinkForTabs`) and routes them after the unlock. The lock does not cover widgets, notification actions or the notification extension. `AppLockSettingsView.swift` is the Settings screen and its row, titled "App lock" (`AppLockBiometry.name` gives the value). `NSFaceIDUsageDescription` is in `Info.plist` and `InfoPlist.xcstrings`. Tests: `ios/PaeoniaAppTests/AppLockModelTests.swift`.
- `ios/PaeoniaApp/App/RootPrivacyLifecycle.swift`: cold-launch and foreground draining and bounded recovery for durable local privacy-purge retries. It blocks a new paired route and sync startup until an older owner-scoped purge has completed.
- `ios/PaeoniaApp/App/MainTabView.swift` and `ios/PaeoniaApp/App/MainTab.swift`: tab layout and high-level feature entry points. `MainTabIdentity` and `MainTabActions` carry the root's data and callbacks, and `MainTabModels` builds the tab view models once. Loads that Home's first frame does not need (topics, games, favorites, reactions, chat summaries) wait for `launchIntroComplete` through `introGatedLoadKey`. `MainTabView+Flows.swift` owns the daily answer covers, streak sheets and deep links. The tabs are Us, Chats, Games, Memories, More. More is the settings screen with a gear icon, and code calls it `settings`, the way the Chats tab is `questions`. The Us tab shows `PairedHomeView`, which code and comments call Home. Deep links, badges and live-feed topics name the tab `us`, and the screen's own views and element IDs keep `home`.
- `ios/PaeoniaApp/App/DeveloperScenarios/`, `ios/PaeoniaApp/App/RootFeatureDependencies.swift`, and the shared `Scenarios` Xcode scheme: Debug-only deterministic state launcher plus interactive local flows through the production root. It replaces sign-in, StoreKit, Convex, APNs, sync and persistence boundaries with in-memory dependencies. Use `PAEONIA_SCENARIO=<id>` or `-paeonia-scenario <id>` for direct UI-test launches. The extension contract is in `docs/developer-scenario-harness.md`.
- `ios/PaeoniaApp/App/RootNoticeLocalization.swift`: root-level user-facing notice copy.
- `ios/PaeoniaAppTests/AccessRouteResolverTests.swift`: access route behavior around launch and relationship access.

When a launch-time network call is cancelled with `NSURLErrorCancelled` / `URLError.cancelled` shortly after render, inspect `.task(id:)` keys before hiding the error.

## Daily challenge

- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeView.swift`: the Chats tab, "Samtaler" in Norwegian and `mainTab.questions` in code. The pinned couple chat comes first, then "Waiting for you" for unanswered partner questions, including older days. Today's unfinished question stays in `DailyPromptCard` and is not repeated there. The hero waits for its answer seal moment through `heroHold` before folding away. `Models/QuestionsTabContent.swift` merges the current snapshot, public topic waiting questions and loaded daily history into one row per question. `Components/DailyChallengeReadCard.swift` is the shared question row for today's list and the earlier days, and `DailyChallengeQuestion.list` (`DailyChallengeQuestion+Rows.swift`) is the shared row-to-question mapping. `Models/DailyChallengeQuestion+Conversation.swift` keeps hidden partner answers out of previews. `Components/SubjectConversationCard.swift` shows memory, story and game chats, and `Challenge/DailyChallengeViewModel+Chat.swift` supplies the chat summaries. The screen owns `DailyChallengeHistoryViewModel`. Memory chats use `MemoryRecord` from `MemoriesViewModel.timeline` and story chats use `Story` from `StoriesViewModel`, joined with summaries by `ThreadChatSummaries.conversations(memories:stories:)` in `MainTabView+Tabs.swift`. A memory with notes and no messages has no row. `MainTabView` loads memories for both tabs, and `MemoryLiveFeed` runs while either tab shows.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/CoupleChatCard.swift` and `Challenge/DailyChallengeView+CoupleChat.swift`: the couple chat ("Just us" / "Bare oss"), the one chat a couple always has that is not about anything in particular. Its card is pinned above everything on the Chats tab, the hero card included, and never appears in today's list or the earlier days. It reads `ThreadChatContext.summaries` (`summary(for: .couple)`, `isUnread(.couple)`), so it is complete on the first frame. `openCoupleChat()` reads the chat with `ThreadChatContext.makeViewModel(subject: .couple, header: nil)` and pushes a `ConversationChatDestination(coupleChat:)` with the tab bar hidden. `paeonia://chat` (`PaeoniaDeepLink.coupleChat`), its push and the in-app message banner open it through `MainTabView.openCoupleChat()`, which sets `isCoupleChatRequested`. A swipe in from the right edge pulls the same chat over any tab, a game or the drawing screen (`Features/Chat/CoupleChatSlideOver.swift`, `ThreadChatScreen.Presentation.slideOver`). `MainTabView.allowsCoupleChatSwipe` turns the swipe off while a chat is open, a sheet or cover never takes it, and a drag that starts on a canvas, a map, Ludo's scene or a `keepsVerticalDrags` board stays with them. `SwipeLessons[.justUs]` and `MainTabView.coupleChatPeekIsWelcome` teach the swipe, and `scripts/scenario-screenshot` starts with it learned. UI test: `ios/PaeoniaAppUITests/CoupleChatJourneyUITests.swift`.
- `ios/PaeoniaApp/Features/Chat/Game/`: one ongoing conversation per couple and game type. `GameChatSubject` owns its stable identity, and `GameConversationSource` identifies a finished round, creation or numbered board game. Buttons ask `MainTabView+GameChat` to open the chat. With a game or game history open in Games, `openGameChat` shows it over the game (`gameChatSheet`, presented by `GameChatPanel`) as a panel on an upright iPhone and a sheet on an iPad or a phone on its side. `GameChatScreen` (`Features/Games/Shared/Layout/GameChatShrink.swift`, applied to every Games destination in `GamesRootView`) draws the Games navigation stack smaller above the panel. `ThreadChatScreen.Presentation` says which chrome the chat gets: pushed, sheet or panel. `GameChatSwipe.swift` holds the swipe up that opens the chat from a game screen and the drag down that closes the panel, and `Shared/Components/SwipeLessons.swift` (`SwipeLessons[.gameChat]`) decides per phone when the chat peeks up under a game. From anywhere else `openGameChat` selects Games, puts the game on top (`showGame`) and opens the chat over it, waiting in `pendingGameChatSheet` while the switch from Chats finishes. `gameChatIsOpen` tells the Games tab a chat is open or on its way, so Mind Meld holds its keyboard. Only a game that can't open yet (Games not loaded, first-time steps due) pushes the Chats destination (`gameChatDestination`). `GameChatResultRow` places each finished game among messages as a pill that opens the existing result or replay, and several with no message between them on the same day fold into one `GameChatResultRunRow` (the projection folds them with `foldingResultRuns`, `ThreadChatViewModel.expandedGameRunIDs` holds the open runs). The user-scoped cache keeps timeline pages and opened results for offline reading and is cleared by the privacy purge. Backend: `gameConversations:get_game_chat_timeline` merges indexed histories and messages under one cursor, and `threads:create_game_thread_with_message` creates the kind-scoped `game_threads` link on the first message. The partner's active games appear above the regular Chats list before any thread exists. `paeonia://daily/game-chat?kind=...` opens the same chat without a summary lookup.
- `ios/PaeoniaApp/Features/Calls/`: the screens for voice and video calls (`docs/calling-plan.md`). The call engine in `Services/Calls/` owns `CallCenter.session`. `View.callOverlay` (`CallOverlay.swift`), mounted once over the tab view and the "Just us" slide-over in `MainTabView+Presence.swift`, puts the full `CallScreen`, the floating `CallBubble` and the `CallRingPill` (the partner's call ringing while Paeonia is open, rung by `CallRinger`, growing out of the partner's avatar where it sits, or at the top of the screen while the avatar is away or the keyboard is up, decided once as it starts: `CallOverlayModel.ringAnchor`) in a window of their own above every screen, sheet and cover, and that window takes touches only on the bubble or the pill while the call is small. The same window shows the partner's avatar when no call is up (`Features/Presence/`), and the avatar and the bubble share one spot, the left or right edge at any height (`CallBubbleSpot`, `CallBubblePlacement`). A drag settles against the edge it was thrown toward, at the height it was dropped. Only the avatar tucks, when a third of it is pushed over the edge or it is flung hard at it. Its tab slides up and down the edge with a drag and stays where it is dropped, and a pull in from the edge brings the avatar out at that height. `CallOverlayModel.touchArea` decides where the window takes touches. `CallOverlayModel` owns whether the call shows full or small (`CallPresentation`). `CallPresentation.after` decides it from each change to `CallCenter.session`, which the model hears through `CallCenter.sessionDidChange`, and the screens and `CallStarter` change it only through the model's methods (`showFull`, `minimize`, `openFull(showing:)`, `openCallout`). The engine never reads it. The bubble and the avatar avoid the bottom controls that report `paeoniaBannerBottomEdge()`, a chat's composer among them, and the game chat panel (`callBubbleBottomEdge`, set in `GameChatPanel`). `CallStarter` is the one start path for the phone buttons (`CallButton` in `GameToolbarActions`, the Us header and the "Just us" top bar) and Call back, with the night question (`CallNightCheck`, on the partner's clock). A call's row in "Just us" is a `ThreadChatMessage` with `call` set, drawn by `Chat/Thread/ThreadChatCallRow.swift`, with no reply, reaction, edit, delete or report. The voice recorders (`ThreadChatComposer`, `DailyVoiceRecorderView`) are off during a call. `CallSoundPlayer` (`Services/Calls/CallSound.swift`) plays the ringback and connected chime when `CallMachine` asks, inside WebRTC's audio engine once it runs. `CallAudio` owns the call's audio session, `CallMediaSession` runs the WebRTC connection for one call, with the shared screens in `CallScreenMedia` and this phone's screen captured by `CallScreenCapture` (ScreenCaptureKit, no extension), `CallCodecs` decides how it compresses audio, video and the screen, and `CallStatsLog` logs codecs, bitrates and network path to the `CallStats` category. `scripts/call-media-probe` checks both on a Mac. `CallQualityTally` (`CallQualityReport.swift`) adds up what the phone measured, and `CallEngine+Quality.swift` sends the report when the call ends, which `scripts/call-reports` prints. `CallEngine+Health.swift` turns `CallConnectionHealth` (a weak connection, from the stats), `CallFrameGaps` (the partner's video standing still, in `CallVideoFeed.swift`) and `CallDevicePower` (heat and battery) into the session's warnings and the video's limits. On the full call screen `CallStageOrder` (`CallStage.swift`) decides which of the partner's camera, the partner's shared screen and the person's own camera fills the screen, `CallStageLayout` places the big one and the previews, turned with the phone (`CallSideways.swift`), and `CallStageView` draws them. `CallTopBarButtons` holds Share your screen and Message, and Message shrinks the call to its bubble and slides "Just us" over the app, as the partner's message notice does (`CallOverlayModel.openCallout`). `CallNotices` says the call's news above the controls and beside the bubble: screen sharing, a weak connection, the offer to turn the camera off, and the partner's callout. Over the app, `CallBubbleLayer` shows the bubble and, while the partner shares, a window with their screen, each a `CallFloatingWindow`. The `call-*` developer scenarios (`DeveloperCallScenarios.swift` and `DeveloperCallStageScenarios.swift`) show every state. The files in `Resources/CallSounds` come from `ios/Scripts/game-sounds.swift`.
- `ios/PaeoniaApp/Features/Presence/` and `backend/convex/appPresence.ts`: the partner's avatar, floating over every screen while both partners have Paeonia open. `PartnerPresenceModel` (run by `MainTabView+Presence.swift`) follows `appPresence:get_partner_presence`, sends the `set_app_presence` heartbeat while the app is in front, and owns "Show when I'm here" (`PresenceSettingsRow` in the Relationship section, which pushes the switch on its own screen). Sign-out sends the leave before the sign-in goes (`RootSystemSideEffecting.leaveAppPresence`). `PresencePillStatus` decides what the avatar says, a callout and a place as its badge, and `PresencePillMode` is how it is drawn (avatar, open toolbar, tucked at an edge) with the notice it shows or keeps until the toolbar closes or the avatar comes back. The avatar is one glass capsule (`PresenceIsland`), the way the Dynamic Island holds a notification: a notice, or the small round Call, Message and Join buttons (`PresenceActions`), widen it toward the middle of the screen while the face stays put. The face alone keeps its own glass, so the whole avatar grows out of a call with the photo. While the capsule shows, one glass sits behind face and content, because glass over glass looks muddy and a `GlassEffectContainer` union stopped drawing the notice's text after any update. When the partner opens a game or the drawing, the capsule opens with the buttons for the notice's few seconds, so Join is one tap. The notice's text is as wide as its words, up to 220 points (`WidthCap`). The heartbeat says whether this person has the widget drawing open (`PresenceViewerPlace.isDrawing`), and goes out at once when that changes, so the partner's avatar shows a pencil and Join opens the drawing. `PresencePillLayer` is a layer of the call overlay window, so the ring pill and the call screen grow out of the avatar. While a sheet, cover or alert is over the app, `PresencePill` draws the avatar as the tab at its side until the person taps it out for that cover, because the cover's own controls sit in its corner, and `PresencePillLayer` checks `PaeoniaAppWindow.isCovered` four times a second while the avatar is on screen. A tap on Call, Message, Join or a callout first closes the sheets and covers over the app. A sheet that holds unsaved work (`interactiveDismissDisabled`) stays, and while one is up the toolbar offers no buttons. Call goes to `CallStarter`, and the rest publish `PartnerPresenceModel.openRequest`, which `MainTabView` opens. Message opens the game's own chat over the game in a game (`PresenceViewerPlace.messageChat`), because its swipe up is easy to miss. With that chat open, or outside a game, Message opens "Just us": it slides over a screen with no chat or with only the game's chat, which it closes, and opens in Chats while another chat is on screen. While the avatar is on screen and no call shows, the partner's news goes to it instead of a banner, because the developer found the toasts noisy. `announcePartnerMessage` sends the partner's messages, and `PaeoniaNotificationRouter.presentForegroundNotice` sends a push from the partner that arrives while the app is open (a letter, a story) as `PresenceNotice.update`. Such a notification shows only while the avatar is out with its toolbar closed (`receiveNow`), and else stays a banner, because it has nowhere to wait. Reminders about the partner (`date_reminder`, `streak_reminder`) stay banners, because they are not the partner's doing (`PaeoniaForegroundNotice.isPartnersDoing`). While a call covers the avatar, the call says the partner's news for the notice's few seconds in a capsule (`CallCallout`, `PartnerPresenceModel.callNotice`), and a tap shrinks the call to its bubble and opens what it is about. `PresenceCallCover` decides what goes there. Under the bubble, or above it in the bottom half of the screen, it says which game or drawing the partner opened, and messages and notifications keep their banners. Above the full call screen's buttons it says messages and notifications as well, because the call screen hides the banners. VoiceOver hears each new notice. The avatar keeps a red count at its top corner of the chats with something from the partner this person has not read (`PartnerPresenceModel.unreadChats`, counted as the Chats list does with `ThreadChatSummaries.isUnread`). A call never makes a notice or a banner, because it rang in the open app, which said how it ended: `announcePartnerMessage` skips call rows and the `missed_call` push is in `typesShownLiveInApp`. The server returns nobody unless both partners show their presence, and reads the partner's open games, the drawing, open chat and typing from their other rooms (`placesInApp` in `lib/presence.ts`). The app keeps the games in the order they opened, so "Opened" and Join name the newest. `DeveloperPresenceScenarios.swift` has the `presence-*` scenarios, `local-flow-presence` and `local-flow-presence-game-chat`, which `PresenceJourneyUITests` drives.
- `ios/PaeoniaApp/Features/Chat/Data/ThreadChatLiveFeed.swift`: live feed for `threads:get_conversation_threads` summaries (posts `LocalStoreDomain.threadChat`). An open game chat follows the common timeline through `liveGameTimelineUpdates`, and an expanded result follows its own authorized detail query. - `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel.swift`: the view model's stored state and init, plus `configure`, `reload`, `apply`, the live update wiring, day-end handling, `startToday`, streak refresh, notices and the home card state. Answering, drafts, sending and chat code live in extensions in the same folder, so shared state is internal rather than private. `apply` drops the active day once its `endsAt` has passed (`DailyChallengeSnapshot.endingCurrentDay(ifEndedBy:)`, injected `now`), and a day-end task re-applies that and reloads, so an ended day never shows as today, even offline. `submitAnswer` refuses an answer after its day ended unless the partner already answered (`Notice.dayEnded`, draft kept) and any text over `DailyAnswerDraft.maxTextLength` (the backend limit), because the server would reject both and the outbox would retry forever. `refreshSendingState` keeps an answer that just left the outbox (`keepingSent`) until the next snapshot says whether it landed, because the outbox marks a send finished before that snapshot arrives. Skip swaps today's question for both partners and is offered only while neither has answered it (`DailyChallengeQuestion.canBeSkipped`) and `hasDraftContent` is false. `shuffle` also deletes the skipped question's staged media, and `applyRestoredStreak` shows a bought-back streak before the server refresh confirms it.

  - `DailyChallengeViewModel+Drafts.swift`: per-question drafts, compose kind, staged media (`stagePhoto`, compressed off the main actor with a per-question token, and `stageVoice`) and the pick-up of drafts the outbox returned.

- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeSnapshot.swift`: today's question (`todayQuestion`) and the open exchanges from earlier days. `questionsAwaitingAnswer` are the questions the partner answered and the user can still answer, and `earlierQuestionsAwaitingAnswer` the ones from earlier days. `homeCardState` is `noChallenge` before today's question exists, `active` until the user answers it, then `complete`.

## Mail

The Us tab card is Mail in English and Post in Norwegian (`HomeMailCard`). A waiting letter shows as a sealed envelope (`waitingMailCard`), one of Home's pop-up cards (`HomePopUpCard`). - `backend/convex/letters.ts` and `lib/letters.ts`: a letter is a note on one of eight template cards, with an optional `letter_image` photo, that one partner writes to the other (`parseLetterBody` owns the length rule and fails with `22001`). `nextLetterState` is the one state machine (`sealed`, `delivered`, `opened`) and `deliverAtFor` decides the arrival once at send: `now`, `at` or `morning` (the recipient's next 08:00 in the zone `resolveMemberStreakTimeZone` gives). `send_letter` inserts the sealed row and schedules `deliver_letter` with `ctx.scheduler.runAt`, or delivers at once. The `deliver-due-letters` cron (`deliver_due_letters`) delivers a sealed letter whose scheduled job was lost, as after a restore. Delivery writes nothing for a deleted letter, a letter already delivered, or a couple that ended, and `notify_letter_arrived` queues `letter_arrived` in its own job, so a push that throws cannot undo the delivery.
  - Reads read no clock and no device. `get_letters` returns the waiting letters (the card and the badge) and the newest received and sent letters, and `get_older_letters` pages further back with a `(time, id)` cursor. A page and its cursor skip letters the reader is not shown, such as a hidden one. The recipient never gets a sealed letter, and a delivered unopened one comes without `body`, `media_asset_id`, `template_key` and `created_at`. Every index range has `deleted_at` in its key, and the recipient's ranges need `delivered_at`, so a sealed letter never re-runs the recipient's reads.

It also returns `partner_birthday`. `send_letter` refuses a `together` letter the composer would not offer at the server's time with `55000`.

It arrives when the author's phone stores a fix that shows the partners together (`noteLocationFix` returns true and `location.ts` calls `deliverMeetingLetters` for the partner), never from the recipient's fix, because the server cannot tell a made-up fix. Otherwise it arrives on the first day of a visit whose first day was set long enough before (`visitLetterTime`, comparing `visits.first_day_set_at`), so the author sees the visit before the letter arrives. `save_visit` sets `first_day_set_at` when it creates a visit or changes its first day. Nothing is scheduled per visit: every run of `deliver_due_letters` starts `sweep_letters_for_visits`, which works out per recipient zone whether the visit's evening has come (`deliverVisitLetters`) and delivers only letters written before that evening (`visitLettersWrittenBefore`), so a letter written after a visit is never brought on by it and a moved or deleted visit needs nothing undone. The `letter_arrived` push for such a letter goes out at once, since it is not a reminder (`waitsWhileTogether`). After a relationship ends such a letter stays sealed and goes with the couple cleanup.
  - `open_letter` (recipient) queues `letter_opened` to the author and answers `P0002` for a deleted letter. `delete_letter` (author) unsends a sealed letter or deletes a delivered one and queues the photo for deletion. The photo is readable by the author at once and by the recipient only once opened (`canReadLetterImage` in `lib/mediaAssets.ts`). Pushes name the partner and never the letter, follow `letters_enabled`, and open `paeonia://mail/<letter id>`. Delivered unopened letters count on the Us tab and the icon (`lib/badges.ts`). The recipient can report an opened letter (`letter` report target). The couple cleanup and purge remove letters, and the export holds only the letters the person wrote. - `ios/PaeoniaApp/Features/Mail/`: `Data/LetterModels.swift` (`Letter`, `MailSnapshot`, `MailPage`, `MailTimeline`, `LetterDelivery`), `Data/LetterBody.swift` (the server's length rule), `Data/LetterTemplate.swift` (the eight cards, art in `Assets.xcassets/Mail/`), `Data/LetterDraft.swift`, `Data/MailCache.swift`, `Data/MailLiveFeed.swift` (`letters:get_letters`, always on for the Us tab badge) and `Data/MailGateway.swift`.

When a send succeeds or the sent list shows the pending letter, it forgets the draft. ## Anniversary recap

- `backend/convex/recap.ts` and `lib/recap.ts`: one `anniversary_recaps` row per couple and anniversary. `startRecap` inserts it with a `counting` state, and `countRecapStep` reads sources a page at a time (at most one `.paginate` per call, since Convex allows one per function), then fills in the all-time numbers and the moments and removes `counting`. The row holds counts and up to three highlight ids, never content, and every count is something both partners can already see. ## Account lifecycle and local privacy

- `ios/PaeoniaApp/App/RootViewModel.swift` (with its `RootViewModel+*.swift` extensions) and `ios/PaeoniaApp/Services/Auth/`: root-owned sign-out and deletion lifecycle, paired profile updates and access re-resolution. Sign-out first calls `PaeoniaSyncService.flushPendingWrites` (time-bounded) so waiting writes go out while the account can still send, then leaves Clerk and purges whatever is still unsent. `AuthNetworkDeadline` caps the network part of sign-in and the profile load at launch (the cached profile opens the app after it). `AppleSignInService` ends an earlier Apple attempt that never reported back as cancelled when a new one starts or its caller is cancelled. Account deletion obtains a fresh Apple authorization code when possible. Cancelling that Apple sheet keeps the account, and any other Apple failure still deletes and shows the manual-revocation step.
- `backend/convex/accountDeletion.ts` and `backend/convex/lib/accountDeletion.ts`: atomic Paeonia-data deletion boundary, relationship ending, device, location and notification cleanup, profile anonymization, retryable deletion jobs drained by a cron, and operator retry functions. `identity:delete_account` is the app-callable action.
- `backend/convex/dataExport.ts`, `dataExportBuild.ts` and `lib/dataExport*.ts`: "Download my data" (GDPR Art. 15 and 20). `lib/dataExportRegistry.ts` lists every table and how it is exported, and `lib/dataExportRegistry.test.ts` fails when a table in `schema.ts` is missing. `request_data_export` queues a job, the Node actions in `dataExportBuild.ts` build zip files, the person gets a push, and signed `GET /data-export` links serve the zips. Design and the scope rule for shared content: `docs/privacy-and-data-export.md`.
- `backend/convex/lib/accountDeletionProviders.ts`: outbound calls for account deletion, Clerk user deletion and Sign in with Apple token revocation. Required environment variables are listed in `backend/AGENTS.md`.
- `ios/PaeoniaApp/Storage/Privacy/`: centralized, idempotent owner-scoped privacy purge. Temporary entitlement loss hides widget, media and location derivatives while preserving drafts and pending work. Permanent relationship loss purges relationship content. Sign-out and account deletion remove all owner SwiftData rows, drafts, caches, widget and App Group files, invite credentials and persisted relationship identifiers.
- `ios/PaeoniaApp/Services/Access/AccessLiveFeed.swift` and `RelationshipEventsLiveFeed.swift`: live subscriptions to `access:get_access_snapshot` and `relationship:get_relationship_sync_events`. The access feed writes the snapshot store (skipping identical snapshots), and `RootViewModel` observes `LocalStoreChanges` for `.access` and re-routes. The events feed saves events, applies them, and persists its cursor only after the apply succeeds. - `ios/PaeoniaApp/Services/Sync/Streams/RelationshipSyncEventApplier.swift`: maps backend `local_purge_scope` hints to temporary-hide or permanent-purge behavior, treating relationship-end `pending_uploads: review` as permanent because no recovery UI exists. Purge-driving events require the sync session's current `relationshipCoupleID`, so an old relationship event cannot erase a newly paired couple's local state, and an unknown relationship identity favors no data loss until Root resolves the access snapshot.
- `ios/PaeoniaAppTests/Sync/LocalPrivacyPurgeTests.swift`, `PaeoniaSyncServiceTests.swift`, `RelationshipEventsLiveFeedTests.swift`, `AccessLiveFeedTests.swift`: owner isolation, idempotence, temporary versus permanent retention, coordinator wiring and cross-couple regression coverage.

## Sync, access, and location

- `ios/PaeoniaApp/Services/Sync/PaeoniaSyncService.swift` and `PaeoniaSyncServiceDefaults.swift`: orchestration for local-first sync work. `SyncClientOperation.swift` and `SyncTypes.swift` are the queued operation envelope and shared types.
- `ios/PaeoniaApp/Services/Sync/Streams/`: the pending operation drain (the offline write outbox) and the relationship event applier. Remote reads do not poll. Each sync run sends every waiting write, oldest first and at most once per run, including writes still waiting out their retry delay, which only sets when the retry timer fires next. A write this build has no handler for stays queued without blocking the writes behind it. Writes the server accepted are deleted at the start of the next run.
- `ios/PaeoniaApp/Services/Live/`: Convex live subscriptions. `LiveQueryService` subscribes, `LiveSyncCoordinator` starts and stops feeds with the session, `LiveFeedRegistry` lists every feed, and `LiveConvexConnection` owns the ConvexMobile client and hands it to feeds only while the socket is logged in as the account signed in to Clerk now. Overlapping `start` calls resolve to the newest session. A feed's `activation` (`LiveFeedTopic.swift`) says whether it always runs or only while a screen needs it. `LiveFeedDemand` takes the topics from the views (`App/MainTabView+LiveFeeds.swift` publishes the visible tab, the games the partner plays, and a touch of the game turns when the app comes to the front or a game push arrives), and `LiveSyncCoordinator+Demand.swift` starts the feeds and stops them a while after their last topic goes. - `ios/PaeoniaApp/Services/Access/AccessRouteService.swift`, `AccessRoute.swift`, `AccessGateway.swift`, `AccessDTOs.swift`: current relationship and access routing.
- `ios/PaeoniaApp/Services/Location/`: foreground location capture, gateway, models and pending operation handling. Concurrent capture requests share one fix. Location uploads the server rejects for good (`42501`, `23514`) stop retrying. `LocationUpdateController` runs the automatic feeds: while the app is open, a live feed reports moves to `LocationMapViewModel.submitObservedLocation`, and while the app is closed it uses the significant-change service, but only when the "Share while Paeonia is closed" choice is on and the person allowed Always. After a new sign-in or relationship it takes the choice the server kept, unless the person sets the switch first. Turning sharing on from the map card or the location primer turns that choice on and asks iOS for Always right away (`offerUpdatesWhileClosed`, called from `RootView.shareLocation`). `BackgroundLocationUploader` sends the position directly, since the outbox only runs while the app is open. `PaeoniaAppDelegate` re-arms it at every launch, and the privacy purge resets it.
- Pausing location sharing: a pause is a sharing choice with an end time, not an off switch. Sharing stays on, nothing is sent, and the server ends the pause by itself.
  - Backend: `location_sharing_preferences.paused_until` (index `by_paused_until`). `location:update_location_sharing_preference` takes `p_paused_until` (only with `p_is_enabled: true`) and keeps the stored location, which only turning sharing off deletes. `update_latest_partner_location` refuses with `42501 location sharing is paused` until the time, and the first update after the time ends the pause itself. The `resume-paused-location-sharing` cron (`location:resume_paused_location_sharing`) clears expired pauses, refreshes the person's own Lock Screen, and for a phone with updates while closed on sends the silent `location_pause_ended` push so it shares where it is now. `lib/locationPause.ts` has `isSharingNow`, which reads the stored pause and not the clock. The "partner shares" check for location pushes uses it, and the Lock Screen distance uses it for the viewer only, so a paused partner's last distance stays. ## Siri and App Intents

- `ios/PaeoniaApp/Features/Siri/`: Siri, Apple Intelligence, Shortcuts and Spotlight. The supported Siri actions, content entities and their enums adopt App Intents schemas (`@AppIntent(schema:)`, `@AppEntity(schema:)`, `@AppEnum(schema:)`). Custom tools use `@AppIntent(.tool)` with iOS 27.3 availability. The build and test wrappers and `swift-typecheck` source `scripts/lib/paeonia-xcode.sh` to select an installed SDK of 27.3 or newer for that process, without changing the machine default. Intents run in the app process. Enum case names are App Intents metadata, so they use manual `siri.*` catalog keys (see `docs/agent-guides/ios-localization.md`). The build checks each type against Xcode's schema list and fails on a missing schema property.
- `Foundation/SiriAccess.swift`: the access gate. `SiriAccess.decide` turns the saved session, the phone's data owner and the cached access snapshot into `.signedOut`, `.notPaired`, `.noAccess` or `.allowed(SiriCouple)`. `RootViewModel.siriAccess()` reads them without the network. Every intent, entity query, photo export and index pass asks it first, and does nothing without access. Tests: `PaeoniaAppTests/Siri/SiriAccessTests.swift`.
- `Foundation/SiriAppContext.swift`: `SiriAppContext.shared`, connected to the root view model in `PaeoniaApp.init` for the production root only. It gives intents the access, `syncAfterLocalChange`, and navigation through `PaeoniaNotificationRouter`. `AppIntent.coupleToActFor()` gates intents that read or change content: without access it throws `needsToContinueInForegroundError`, and with App Lock on it continues in the foreground and waits for `AppLockModel` to unlock (`activationCount` tells it the lock has decided). `coupleToOpenFor()` gates open and search intents, which open the app anyway, so App Lock's cover hides what they open.
- `Foundation/SiriContent.swift`: builds the entities from the caches the screens read (dates from `CoupleDatesViewModel`, memories from `loadCachedMemories` grouped by `MemoryTimeline`).
- `Foundation/SiriEntityIndexer.swift`: keeps the named Spotlight index `no.paeonia.app.entities` equal to what the person sees. It starts in `PaeoniaApp.init`, so it also runs when an intent launches the app in the background, and follows `LocalStoreChanges`. One pass runs at a time. The index follows the local caches, so after a new sign-in the memories appear once the Memories feed has run.
- Privacy purge: `LocalPrivacyPurgeService.purgeRetryably` calls `SiriEntityIndexClearing.removeAllEntities()` after the record purge, for every scope. A failure keeps the purge request queued, and the retry removes the index again. A removal bumps a generation, so an index pass that started earlier never writes after it. Photos from other apps that wait in `MemoryPhotoInbox` go with the other owned drafts. Tests: `PaeoniaAppTests/Siri/SiriIndexPrivacyPurgeTests.swift`. Purge tests pass `FakeSpotlightIndex`, because the real index answers slowly in the unit-test host.
- `Calendar/`: `CoupleCalendarEntity` (`.calendar.calendar`, the one "Our dates" calendar), `CoupleDateEntity` (`.calendar.event`, id `CoupleDateID.countdown(UUID)` or `.birthday(userID:)`) and `CoupleDateAttendee`, which the schema requires and Paeonia leaves empty. `CoupleDateIntents.swift` creates, updates, deletes and opens (`.system.open`, the dates timeline). Writes go through `CoupleDatesViewModel`, the editors' queued path (`CoupleDateWrites`).
- `Photos/`: `MemoryAlbumEntity` (`.photos.album`, one per memory) and `MemoryPhotoEntity` (`.photos.asset`, id `MemoryPhotoID.saved(mediaAssetID:)`, or `.incoming(UUID)` for a photo from another app). A photo exports as JPEG through `MemoryMediaImageService` and imports from another app into `MemoryPhotoInbox`. `MemoryIntents.swift` opens a memory or photo (`PaeoniaDeepLink.memoryPhoto`), `createAssets` stages the files and opens the new-memory form with them (`PaeoniaDeepLink.newMemory`, since a memory needs a title), and rename, delete and add or remove photos go through `MemoriesViewModel.saveEdits` and `deleteMemory` (`MemoryWrites`). The photo-editing properties the schema requires stay empty, and Paeonia adopts no photo-editing intents.
- `Messages/`: `ChatPersonEntity`, `ChatConversationEntity` and `ChatMessageEntity` adopt the Messages schemas, `IndexedEntity` and shared ownership. `SiriChats` reads the chat summaries, messages and pending sends through `ThreadChatService` and includes an empty "Just us" conversation before the first send. Private topic chats (Flirt) and question chats whose privacy is not yet known are excluded from Siri and Spotlight. A cached voice message's body is its transcript. Send and unsend use the chat service's outbox, and edit, reaction and read status use the same service methods as the chat UI. Marking unread returns an explanation because the app has no unread-marking action.
- `Messages/ChatSendIntents.swift`: the required send and draft group. A partner destination goes to "Just us". The destination union accepts only Paeonia person entities, because generic Contacts identifiers cannot identify a Paeonia partner. Attachments, voice input, subjects and scheduled sends return an explanation rather than losing part of the request. Draft opens the selected chat and appends its text to the composer (`SiriAppContext.messageDraft` holds the text until the composer consumes it, and every privacy purge clears it). The SDK's union macro needs a `nonisolated` type display property under the app's default MainActor isolation.
- `Messages/ChatMessageIntents.swift`: schema edit, unsend and read actions. Reaction is an authenticated custom Siri tool on iOS 27.3 that sets one emoji through `ThreadChatService.setReaction`.
- `Daily/`: custom tools read today's question, start the shared day through `DailyChallengeViewModel.startToday` when it has no active question, and submit a text answer for that exact instance through `DailyChallengeViewModel.submitAnswer`. Entity lookup and answering never start a replacement day, and they refuse rollover, an existing answer or queued send, existing drafts, incompatible answer kinds and excessive text. The active daily model is shared through `SiriAppContext` so unsaved composer text is respected. Success means durable local enqueue, not server delivery.
- Custom Siri tools require the iOS 27.3 Siri AI Developer Preview on an Apple Intelligence device in a supported region. Apple supports development-signed builds and internal TestFlight testers during this preview, not external TestFlight or App Store builds. Build with `DEVELOPER_DIR=/Applications/Xcode-27.3.0-beta.app/Contents/Developer`, and the app's minimum target remains iOS 27.0. See [Apple's preview availability](https://developer.apple.com/documentation/appintents/siri-ai-developer-preview).
- `Messages/PaeoniaChatShortcuts.swift`: publishes app-scoped send, draft, edit, unsend and reaction phrases through `AppShortcutsProvider`. `Resources/Localization/AppShortcuts.xcstrings` supplies English and Bokmal phrases, and app startup calls `updateAppShortcutParameters` to register them. Speech recognition still needs device verification.
- Notifications: message pushes include `thread_id` and `message_id` for every chat kind. The app passes the message id through `PaeoniaForegroundNotice` and annotates its foreground banner with the real `ChatMessageEntity`. The communication-notification extension must not hold an App Entity reference: AppIntentsTesting then resolved the message through the notification-service extension and failed with `LNConnectionErrorDomain` 1100, because that extension point cannot serve the query. Background announcement context therefore stays unavailable.
- `System/SearchPaeoniaIntent.swift`: `.system.searchInApp` opens Search with the words typed in (`PaeoniaDeepLink.search`, `SearchViewModel.begin(query:)`).
- Onscreen awareness: memory cards (`MemoriesScreen`) and the countdown and birthday rows of the dates timeline (`RelationshipTimelineView`) carry `.appEntityIdentifier`. Chat message rows carry message identifiers, and the open chat publishes its conversation in `NSUserActivity`. The open memory publishes an `NSUserActivity` with the memory's entity, and each photo in its carousel carries its photo's entity (`Photos/MemoryOnScreenForSiri.swift`).
- Every intent that reads or changes content sets `authenticationPolicy = .requiresLocalDeviceAuthentication`. With the Xcode 27.3 SDK, private entities also require it, and the daily prompt property declares the same policy. These controls protect Siri responses and do not establish that Spotlight hides indexed text while locked. By the developer's decision, both partners' visible memory notes are indexed as text on `MemoryAlbumEntity.searchableAttributes`, and hidden and deleted notes stay out through `visibleBody`.
