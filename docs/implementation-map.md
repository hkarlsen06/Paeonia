# Implementation Map

This is the first stop when an agent needs to find the current owner of a Paeonia behavior. Keep this file factual and source-oriented; durable rules still belong in `AGENTS.md`.

## Launch, Root State, And Navigation

- `ios/PaeoniaApp/App/RootView.swift`: root body, root banner mounting, and the cold-launch intro (`LaunchExperienceView`), which stays up until the intro signals it has fully unmasked the app (not just when `state` leaves `.launching`). `RootView+Screens.swift` maps each `AppState` to one screen and puts profile setup, the paywall, pairing, joining and the account notices in `PaeoniaScreenFrame` (`Shared/DesignSystem/Components/PaeoniaScreenFrame.swift`), so only their content crossfades. The logo shows on the welcome screen only. `PaeoniaScreenScroll` in the same file sets a screen's content a little above the middle of the space over its bottom bar and scrolls when it does not fit; `RootView+Actions.swift` forwards user actions and reacts to session, state, and invite-code changes (an invite link opened while paired is dropped with a banner); `RootView+System.swift` owns deep links, widget sync, push registration, and the foreground pass (one pass at a time); `RootView+PermissionPrimers.swift` asks for nothing when the app opens. The primers wait until the person has answered a question or sent a drawing (`MainTabActions.sentSomethingToPartner`, called when the answer cover or the drawing screen closes). The notification primer comes first, and at most one primer shows per visit. The foreground pass refreshes location next to the sync, so content never waits on GPS.
- `ios/PaeoniaApp/App/PaeoniaApp.swift`: builds `RootViewModel` and `LocationMapViewModel` once (after Clerk is configured) and gives the root view model a Clerk session check, so a session that ends while the app runs is noticed.
- `ios/PaeoniaApp/Features/Auth/LaunchExperienceView.swift`: the cold-launch overlay. It looks exactly like the system launch screen and holds only until `contentReady`, then fades out over the first app surface in 0.24 s and stops taking touches as the fade starts. Nothing in it moves, so the fade can overlap the system's own launch screen fade or the app lock's cover, which show the same mark, without showing two marks. `LaunchScreenCanvas.swift` draws `LaunchBackground` and `PaeoniaLaunchPetalMark` as `UILaunchScreen` in Info.plist does and fades them with Core Animation. The first surface builds in the update that starts the fade (80 to 117 ms on an iPhone), and a SwiftUI animation would lose that much of the fade.
- `ios/PaeoniaApp/Features/Auth/LaunchReveal.swift`: the coordination glue between the overlay and the surface it uncovers. `EnvironmentValues.launchContentRevealed` flips true as the overlay starts to fade, and `EnvironmentValues.launchIntroComplete` once it has faded. Both are set on the routed content in `RootView` and default to `true` outside the cold launch. The file also has reusable entrance modifiers for surfaces that still use a staggered entrance. `PairedHomeView` keeps its Home cards stationary on cold launch. Compact-width Home uses `HomeMapLayout`, whose map intro waits on `launchContentRevealed` and for the app to be active, so it does not play under the App Store's purchase sheet or a system alert. The regular-width `CoupleMapCard` flame sweep waits on `launchContentRevealed` too.
- `ios/PaeoniaApp/Features/Auth/AuthBaselineViews.swift`: `AuthLaunchingView`, the quiet, copy-free loading surface shown under the cold-launch intro. Also the deleting-account and relationship-ended screens. Scenarios `onboarding-usage`, `relationship-ended`, `account-closed` and `deleting-account` open the single-purpose screens after sign-in in their frame.
- `ios/PaeoniaApp/Features/Auth/Onboarding/AuthOnboardingView.swift`: profile setup after the first sign-in (a name and a cropped photo, both required; an imported Google photo counts). `AuthOnboardingPhotoField.swift` is the photo picker: an empty dashed circle that asks for a photo, and after Continue without one a shake, a warm glowing ring and a callout that opens the picker (`AuthOnboardingPhotoNudge` counts the taps). A missing name only brings up the keyboard once there is a photo. Scrolls, keeps Continue above the keyboard with a loading state, and puts sign out and delete account in quiet links under it. The start date is asked before sign-in (`Welcome/WelcomeStartDateStep.swift`).
- `ios/PaeoniaApp/Features/Auth/Welcome/`: the signed-out flow. `WelcomeFlowModel.swift` is the state machine (`WelcomeStep`: welcome, start date, drawing, sign-in with a `WelcomeSignInMode` of start, joining or returning), and `WelcomeFlowView.swift` crossfades the steps. Only the welcome screen shows the logo. Every later step sits in `PaeoniaScreenFrame`, the same frame as the screens after sign-in, with Back at the top level with the drawing screen's back button. `WelcomeView.swift` is the first screen: the `PaeoniaWordmark`, `WelcomeWidgetDoodle.swift` (a Home Screen drawing widget tile where a partner's handwritten note writes itself in once on launch, stroke by stroke with a tapered pen; the strokes are in `WelcomeDoodleInk.swift`, "miss you" in English and "savner deg" in Norwegian; touching the canvas clears the note and lets the person draw with the app's pen in `WelcomeFingerDoodle.swift`. Start our space carries that doodle to the first drawing: it waits in `WelcomeFlowStore` as `carriedDoodle` and `WidgetDrawingViewModel.addStrokesOnceLoaded` puts it on the draft once the canvas has loaded, one undo step per stroke. Every other way out drops it), the headline "Draw something. It shows up on their Home Screen.", then "Start our space", "I was invited" and "I already have an account". "I was invited" opens `PairingCodeEntrySheet`. When the clipboard holds a link, which the `/join` web page copies before sending a partner to the App Store, that row becomes a system Paste button. A pasted join link saves its code, and anything else opens the code sheet. A saved code (from there, a link, or the sign-in step's Change code) moves on to sign-in for joining, and the join screen opens for it after profile setup. The start path is `WelcomeStartDateStep.swift` (the date and `RelationshipDaysReveal`; the date waits in `WelcomeFlowStore.swift` and goes into the outbox as `FirstDayStartedOnQueue`, kind `setFirstDayStartedOn`, when `RootView+Actions.sessionChanged` sees a session), then `WelcomeDrawingStep.swift`: the real `WidgetDrawingView` with no owner, couple or live relay and without its share button or "Not sent yet" pill, and `WelcomeDrawingUploader.swift`, whose send only marks the saved drawing `isFirstDay`. Before sign-in the drawing and its marker live in `WelcomeDrawingStorage.swift`, a canvas in `Application Support/WelcomeDrawing` and a marker under its own key, apart from the widget's, so another account's data left on the phone (`RootDeviceOwnerStore`) never shows on the canvas and clearing it at sign-in (`RootViewModel.clearDataFromAnotherAccount`) never reaches the drawing. The drawing then lands on `WidgetHomeScreenMock`. After that clearing, `WelcomeFlowModel.sessionStarted` moves it to `WidgetCanvasService.shared` with the `isFirstDay` marker in `WidgetPendingUploadStore.shared`, and the invite screen sends it (`InviterFirstDayModel.load`). Choosing to join or to sign in to an existing account drops it. `WelcomeSignInStep.swift` has `WelcomeSignInPicture` (the waiting first drawing on the Home widget card's tile, rendered by `WelcomeFlowModel.waitingDrawingImage`, or else `WelcomeHero`, the pink and lavender peonies from the `Welcome` asset folder, sized to the free height), the headline per mode, white Continue with Apple, Continue with Google, the saved-code row for joining, and in-app privacy, terms and support links. Only the tapped provider shows a spinner (`RootViewModel.signingInWith`). Someone who signed in on this phone before opens at sign-in for returning, with Back to welcome. Deleting the account starts over at welcome. `WelcomeFunnelRecorder.swift` counts how many installs reach each step (see `backend/convex/onboarding.ts`): once per step per install, the step name only, no auth header, not PostHog. Scenarios `welcome`, `sign-in`, `sign-in-invite`, `welcome-start-date`, and `local-flow-fresh` for the whole journey.
- `ios/PaeoniaApp/App/RootViewModel.swift`: root auth/access/pairing state. `RootRoute.swift` is the route enum; while access resolves after sign-in or profile setup the route holds that screen (with its button spinner) instead of showing an empty one. The selected tab resets to Home whenever the state leaves `.paired`. `RootViewModel+Account.swift` owns sign-in, sign-out, deletion (cancelling the Apple re-sign-in sheet keeps the account), profile saves (success is reported once the profile is saved; sync follows), and sessions that end on their own (back to sign-in with a banner, local data kept). `RootDeviceOwnerStore.swift` remembers whose data is on the phone, so signing in as someone else clears it like a sign-out. Installs from before the marker use the widget's saved identity instead. `RootViewModel+Launch.swift` is the cold launch: `PaeoniaApp.init` calls `beginLaunch()`, which starts the session restore (`ClerkAuthService.restoreSession`, one `identity:launch` call that returns the profile and the access snapshot) and reads the saved state before the scene exists, and `start()` awaits them. `RootViewModel+AccessResolution.swift` resolves access. `showSavedLaunchPreview()` opens Home on the first frame from the saved session and a saved paired snapshot (only when the phone holds this account's data and no privacy purge is pending), without committing the route, purging or celebrating, and the launch result settles it. Other saved states wait for the server. Without a launch result, a slow cold launch shows a saved paired snapshot after one second. `RootViewModel+Sync.swift` starts sync and stops if the session ended during startup. `RootViewModel+Refresh.swift` re-checks access after a purchase, a renewal, or a pairing change without restoring the session, so a failed check never signs anyone out. `RootViewModel+State.swift` holds the read-only state the views use. `RootPairingCelebrationState.swift` decides when the celebration and the first day sequence after it show. Tests in `ios/PaeoniaAppTests/RootViewModelFlowTests.swift`, `RootViewModelLaunchTests.swift` and `RootSessionLifecycleTests.swift`.
- `ios/PaeoniaApp/Features/AppLock/`: the optional Face ID, Touch ID or passcode lock. It is off by default, stored on the phone only (`UserDefaultsAppLockStore`, keys `paeonia.appLock.*`), and cleared by the sign-out and account deletion purge (`LocalPrivacyPurgeService`, `AppLockModel.shared.reset()`). `AppLockModel` decides the state. A cold launch starts locked. A trip to the background locks when the time away reaches the chosen grace (`AppLockPolicy`, Right away, 1 minute by default, or 15 minutes; measured with `ContinuousClock`). An app that only became inactive (Control Center, a system sheet, the Face ID prompt) never locks, but shows the cover as a shield so the app switcher snapshot stays blank. `AppLockCoverController` puts `AppLockCoverView` in its own `UIWindow` above everything, including sheets, and feeds the model the `UIScene` activate, deactivate and background notifications synchronously. The cover continues the launch screen (same petal mark, same place) and shows the Unlock button only when locked. The prompt opens by itself on launch and on return from the background, and never again after a cancel. `LocalAuthenticationAppLockAuthenticator` uses `.deviceOwnerAuthentication`, so the phone's passcode is always the fallback. A phone that lost its passcode turns the lock off and shows a banner, so nobody is locked out, and the lock cannot be turned on without a passcode. Turning it on or off needs a successful authentication. `AppLockRootModifier` is mounted on the routed content in `RootView+Screens.swift` (installs the cover, provides `AppLockModel` in the environment, shows the banner). While locked, `RootView+System.swift` holds deep links and notification taps (`isHeldByAppLock`, `deepLinkForTabs`) and routes them after the unlock. The lock does not cover widgets, notification actions or the notification extension, and the settings footer says so. `AppLockSettingsView.swift` holds the Settings screen and its row (the App section, hidden when the environment has no model, as in developer flows). The row and button name the right biometry (`AppLockBiometry.name`). `NSFaceIDUsageDescription` is in `Info.plist` and the localized `InfoPlist.xcstrings`. Tests in `ios/PaeoniaAppTests/AppLockModelTests.swift`.
- `ios/PaeoniaApp/App/RootPrivacyLifecycle.swift`: cold-launch/foreground draining and bounded recovery for durable local privacy-purge retries; blocks a new paired route and sync startup until an older owner-scoped purge has completed.
- `ios/PaeoniaApp/App/MainTabView.swift` and `ios/PaeoniaApp/App/MainTab.swift`: tab layout and high-level feature entry points. `MainTabIdentity` and `MainTabActions` carry the root's data and callbacks; `MainTabModels` builds the tab view models once. The loads that Home's first frame does not need (topics, games, favorites, reactions, chat summaries) wait for `launchIntroComplete` through `introGatedLoadKey`. `MainTabView+Flows.swift` owns the daily answer covers, streak sheets, and deep links (each link checks it is still current after its refresh). The tabs are Us, Chats, Games, Memories, More. More is the settings screen with a gear icon, and code calls it `settings`, the way the Chats tab is `questions`. The Us tab shows `PairedHomeView`, which code and comments call Home. Deep links, badges and live-feed topics name the tab (`us`), and the screen's own views and element IDs keep `home`. Each tab icon is an SF Symbol.
- `ios/PaeoniaApp/App/DeveloperScenarios/`, `ios/PaeoniaApp/App/RootFeatureDependencies.swift`, and the shared `Scenarios` Xcode scheme: Debug-only deterministic state launcher plus interactive local flows through the production root. It replaces sign-in, StoreKit, Convex, APNs, sync, and persistence boundaries with in-memory dependencies. Use `PAEONIA_SCENARIO=<id>` or `-paeonia-scenario <id>` for direct UI-test launches. The extension contract is in `docs/developer-scenario-harness.md`.
- `ios/PaeoniaApp/App/RootNoticeLocalization.swift`: root-level user-facing notice copy.
- `ios/PaeoniaAppTests/AccessRouteResolverTests.swift`: access route behavior around launch and relationship access.

When a launch-time network call is cancelled with `NSURLErrorCancelled` / `URLError.cancelled` shortly after render, inspect `.task(id:)` keys before hiding the error. The known Daily Challenge case is documented in `AGENTS.md`.

## Daily Challenge

- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeView.swift`: the Chats tab, "Samtaler" in Norwegian and `mainTab.questions` in code. The pinned couple chat comes first, then "Waiting for you" for unanswered partner questions, including older days. Today's unfinished question stays in `DailyPromptCard` and is not repeated in that section. The hero waits for its answer seal moment through `heroHold` before folding away. `Models/QuestionsTabContent.swift` merges the current snapshot, public topic waiting questions and loaded daily history. It keeps one row per question, prioritizes an unanswered round, and orders the remaining question, memory, story and game conversations by latest activity regardless of read state. Question activity uses the later of the latest answer and an available chat's latest message. Topics navigation stays below unanswered questions and above the full conversation list. `Components/DailyChallengeReadCard.swift` shows a dated, compact question title, sender-labeled message or visible answer preview, and answer status. `Models/DailyChallengeQuestion+Conversation.swift` keeps hidden partner answers out of previews. `Components/SubjectConversationCard.swift` shows memory, story and game chats with a date and sender-labeled preview. `Challenge/DailyChallengeViewModel+Chat.swift` supplies the chat summaries and prepares question chats. The screen owns `DailyChallengeHistoryViewModel`, loads it on appear, refresh and couple-day changes, and preserves its failure and retry UI. Older answer rounds remain inside the question's chat. Memory chats use `MemoryRecord` from `MemoriesViewModel.timeline`, story chats use `Story` from `StoriesViewModel`, joined with summaries by `ThreadChatSummaries.conversations(memories:stories:)` in `MainTabView+Tabs.swift`. A memory with notes and no messages has no row. Tapping a subject conversation prepares `ThreadChatScreen` with its header and hides the tab bar. `MainTabView` loads memories for both tabs, and `MemoryLiveFeed` runs while either tab shows.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/CoupleChatCard.swift` and `Challenge/DailyChallengeView+CoupleChat.swift`: the couple chat ("Just us" / "Bare oss"), pinned above everything else on the Chats tab. The card blends toward both partners' petal colors and shows both faces joined by a heart, so it never looks like a question row. The pink outline and glow still mean only "waiting for you". It shows the newest message or a line that invites the first one, and opens the chat without a header card. `paeonia://chat` (`PaeoniaDeepLink.coupleChat`) opens it from its push. UI test: `ios/PaeoniaAppUITests/CoupleChatJourneyUITests.swift`.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel.swift`: the view model's stored state and init, plus `configure`, `reload`, `apply`, the live update wiring, day-end handling, `startToday`, streak refresh, notices, the home card state. The answering, drafts, sending, and chat code lives in extensions in the same folder, so state shared across files is internal rather than private. `apply` drops the active day once its `endsAt` has passed (`DailyChallengeSnapshot.endingCurrentDay(ifEndedBy:)`, with an injected `now` clock), and a day-end task re-applies that and reloads at the end of the day, so an ended day never shows as today, even offline. `submitAnswer` refuses an answer after its day ended unless the partner already answered (`Notice.dayEnded`, draft kept) and any text over `DailyAnswerDraft.maxTextLength` (2,000 code points, the backend limit), because the server would reject both and the outbox would retry forever. `isSending` turns false as soon as the snapshot carries the sent answer. `refreshSendingState` runs on every live apply and on `.pendingOperations` changes, and skips a store read that started before a newer local send (`sendingGeneration`). On a `.pendingOperations` change it keeps an answer that just left the outbox (`keepingSent`) until the next snapshot says whether it landed, because the outbox marks a send finished before that snapshot arrives. Without that, today's card turns back into the question for a moment after sending. A draft the outbox returned ends the sending state at once. On outbox changes it also picks up answers the outbox put back into the drafts and raises `Notice.submitFailed`. Skip swaps today's question for both partners and is offered only while neither has answered it (`DailyChallengeQuestion.canBeSkipped`). It is also gated on `hasDraftContent` (anything typed or staged), not on whether the draft can be sent. Photos are compressed off the main actor in `stagePhoto` with a per-question token, so a removal, skip, or newer pick wins, and Send waits for the photo. `shuffle` also deletes the skipped question's staged media. `applyRestoredStreak` shows a bought-back streak before the server refresh confirms it.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel+Answering.swift`: `submitAnswer` and the outbox enqueue, the text and partner-choice edits, and `shuffle` (skip).
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel+Drafts.swift`: the per-question drafts, compose kind, staged photo and voice media (`stagePhoto`, `stageVoice`), and the pick-up of drafts the outbox returned.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel+Sending.swift`: the "saved, sending" state (`SendingAnswer`, `isSending`, `sendingPreview`, `refreshSendingState`), rebuilt from the pending operations.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel+Chat.swift`: the chat and history view model factories, `prepareChat`, thread summaries, unread chats, and the partner-answer seen state (`hasNewFromPartner`, `uploadSeenPartnerAnswers`).
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeNoticeLocalization.swift`: localized title/message mapping for `DailyChallengeViewModel.Notice`.
- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeSnapshot.swift`: today's question (`todayQuestion`) and the open exchanges from earlier days. `questionsAwaitingAnswer` are the questions the partner answered and the user can still answer, `earlierQuestionsAwaitingAnswer` the ones from earlier days, which the cards list as locked rows. `homeCardState` is `noChallenge` before today's question exists, `active` until the user answers it, then `complete`.
- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeModels.swift`: UI/domain models and answer-kind shape. Both partners answer the same question, so a question has no owner: `isAwaitingCurrentUserAnswer` is a question the partner answered and the user can still answer. `DailyChallengeQuestion` carries `earlierRoundCount`, `latestEarlierRoundLocalDate` and `hasSharedRound`. `hasRevealedPartnerAnswer` is per round (the new-answer marks use it) and `isChatAvailable` is per question (`hasRevealedPartnerAnswer || hasSharedRound`).
- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeRemoteRows.swift`: DTOs matching the `backend/convex/daily.ts` function results. Question rows carry `earlier_round_count`, `latest_earlier_round_local_date` and `chat_available` (see the question chat paragraph under `Chat/`).
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeService.swift`: Convex calls for challenge/day/question/answer behavior.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeDraftStore.swift`: local answer draft persistence.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeSnapshotCache.swift`: local-first cold-launch cache. The live service writes the raw `DailyChallengeRemoteSnapshotRow` (keyed per user) on every successful snapshot load; `DailyChallengeViewModel.configure` seeds `snapshot`+`streak` from it via `DailyChallengeRemoteSnapshotRow.loadResult` before the network `reload()`, so returning users see real content (not placeholders) on the first frame. The centralized local privacy purger clears it on relationship access loss or user departure.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeLiveFeed.swift`: live feed for today's challenge. It follows `daily:get_daily_challenge_snapshot` for the known couple day, or `get_today_daily_challenge_snapshot` when no day exists yet. Every today subscription (and every one-shot `loadTodaySnapshot`) uses a fresh random `p_day_key`, because the couple day ends at the westmost partner's midnight, not this phone's, so a per-local-date key could be served a stale result. Without a day the today subscription is renewed every half hour or at local midnight. Each result goes into the snapshot cache through `DailyChallengeLiveWriteClock` and posts `LocalStoreDomain.dailyChallenge`; `DailyChallengeViewModel` re-reads the cache and applies it. It never starts a day.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/CoupleChatCard.swift` and `Challenge/DailyChallengeView+CoupleChat.swift`: the couple chat ("Just us" / "Bare oss"), the one chat a couple always has that is not about anything in particular. Its card is pinned above everything on the Chats tab, the hero card included: both partners' avatars, the newest message as "You: ..." or "<partner>: ...", or "Write to <partner> about anything" before anyone wrote, plus the unread dot and the attention glow. It reads `ThreadChatContext.summaries` (`summary(for: .couple)`, `isUnread(.couple)`), so it is complete on the first frame. `openCoupleChat()` reads the chat with `ThreadChatContext.makeViewModel(subject: .couple, header: nil)` and pushes it as a `ConversationChatDestination(coupleChat:)` with the tab bar hidden. The chat has no header card. `paeonia://chat` (`PaeoniaDeepLink.coupleChat`), its push and the in-app message banner open it through `MainTabView.openCoupleChat()`, which sets `isCoupleChatRequested` for the screen. It never appears in today's list or the earlier days. `CoupleChatJourneyUITests` opens it from Chats and sends a message in `local-flow-game-conversation`.
- `ios/PaeoniaApp/Features/Chat/Game/`: one ongoing conversation per couple and game type. `GameChatSubject` owns its stable identity, while `GameConversationSource` identifies a finished round, creation or numbered board game. Buttons ask `MainTabView+GameChat` to open the chat. With a game or game history open in Games, `openGameChat` shows it as a sheet over the game (`gameChatSheet`, `ThreadChatScreen` with `embedsNavigationStack`). Anywhere else it pushes the Chats destination (`gameChatDestination`). `GameChatResultRow` places compact results among messages and expands the existing full result or replay. The user-scoped cache keeps timeline pages and opened results for offline reading and clears them during a privacy purge. `gameConversations:get_game_chat_timeline` merges indexed histories and messages under one cursor. `threads:create_game_thread_with_message` creates the kind-scoped `game_threads` link on the first message. The partner's active games appear above the regular Chats list before any thread exists. `paeonia://daily/game-chat?kind=...` opens the same chat without a summary lookup.
- `ios/PaeoniaApp/Features/Chat/Data/ThreadChatLiveFeed.swift`: live feed for `threads:get_conversation_threads` summaries (posts `LocalStoreDomain.threadChat`). An open game chat follows the common timeline through `liveGameTimelineUpdates`, and an expanded result follows its own authorized detail query. Other chats follow `threads:get_thread_messages` through `ThreadChatServicing.liveMessageUpdates` and the question's days through `liveRoundUpdates` (see `Chat/` below), which merges each result into `FileThreadChatCache` and links server copies of still-sending messages to their operations (`ThreadChatMessage.claimingPending`).
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengePendingOperationHandler.swift`: local-first retry handling for queued challenge writes. A submit the server refuses for good (`23514`, `23505`, `22023`) becomes a terminal failure and the answer goes back into the drafts (`DailySubmitAnswerOperationPayload.Content.restoredDraft`), which `DailyChallengeViewModel` picks up when the drain posts `.pendingOperations`. Upload errors and access errors (`42501`) keep retrying. `DailyChallengeLiveWriteClock.notePurge()` (called from the snapshot cache's `clearAll`) stops a response that was in flight during a privacy purge from writing the couple's content back.
- `ios/PaeoniaApp/Features/Chat/`: the one chat for every conversation. It has the page (`ThreadChatView`) and view model (`ThreadChatViewModel`), the thread/message RPC service (`ThreadChatService`), the owner-scoped local cache (`FileThreadChatCache`), optimistic merge rules, and pending-operation handlers for lazy thread creation and sends. The chat copies Tidex's friends chat (`~/repo/Tidex/ios/TidexApp/Features/Friends/Messages/`) on the same `hkarlsen06/Chat` fork commit: `.animateMessageUpdates(false)`, a custom composer through `inputViewBuilder`, a zero-height `betweenListAndInputViewBuilder`, day dividers, and the long-press menu (`Thread/ThreadChatMenuAction`). `Thread/ThreadChatProjection` builds ExyteChat's messages and the row models once per data change and folds everything a row draws into `triggerRedraw`, so ExyteChat redraws only rows that changed. `Thread/ThreadChatMessageRow` draws Paeonia's question (logo avatar), the answers, and messages, with grouped bubble corners, quotes above replies, voice messages, and a Sending / Sent / Not sent line. `Thread/ThreadChatGestures` and `Thread/ThreadChatGestureBridges` are the Tidex swipe gestures: swipe a bubble toward the middle to reply, swipe left to show times, swipe right to go back. Answers take the reply swipe too. A reply carries a `ThreadChatItemID` for a message, an answer or a finished game result. The wire fields are `p_reply_to_message_id`, `p_reply_to_answer_id` and `p_reply_to_game_result_source`. A first message can reply to an answer or a result. Game results have no generic reaction target. Reactions, like Tidex's: long-pressing a sent message or a readable answer, the user's own included, shows ExyteChat's reaction row (`ReactionPalette`: the person's recent picks first, filled up with the usual six, kept in `UserDefaults` and cleared on sign-out, plus emoji search), and choosing the reaction already there takes it back. Each person has one reaction per item, keyed by `ThreadChatItemID` (a message or an answer, the same id a reply uses). `ThreadChatViewModel+Reactions` keeps the change in its own `ReactionEditor` (see Reactions) and saves it straight through `reactions:set_reaction`, not the send queue, and a refusal puts the earlier reaction back with a banner. Message reactions arrive on each message row (`ThreadChatMessage.reactions`) and answer reactions with the rounds (`DailyQuestionChatRoundsRow.reactions`). `ReactionBadge` draws them on the bubble's top corner. `Thread/ThreadChatComposer` is the text field and reply banner, and its microphone records with `DailyVoiceRecorder` (the voice-answer recorder). Replies send `p_reply_to_message_id` to `threads:send_thread_message`, and the long-press menu reports a partner message as a `thread_message` target. Edit: for 5 minutes after sending, the menu offers Edit on your own text messages and photo captions, never on answers or voice messages. The composer shows `Thread/ThreadChatEditBanner`, holds the earlier draft until the edit ends, and saves straight through `threads:edit_thread_message` instead of the send queue. The server checks the sender and the 5-minute window and sets `edited_at`, and the live `get_thread_messages` query brings the new text to both phones. The row adds Edited to the small line under the bubble, next to Sent or Read. Delete: the long-press menu offers Delete on any message of your own (text, photos, voice) with no time limit, behind a confirmation dialog (`Thread/ThreadChatDeleteConfirmation`). `threads:delete_thread_message` keeps the row as a tombstone (`deleted_at` set, text and reactions removed, media queued for storage deletion), and `get_thread_messages` returns it with no text, media or reactions. Both phones draw `Thread/ThreadChatDeletedNote` ("You deleted this message") in its place, and a reply that quoted it says the message was deleted. Delete works offline like a send: `ThreadChatService+Deleting` queues a `delete_thread_message` operation (`DeleteChatMessageOperationHandler`), shows the tombstone at once, and re-applies pending deletes to every server result (`withDeletions`) so a late live result cannot bring the message back. A message that was never tried is removed from the send queue with `PendingSyncOperationPersisting.discardUnsent` and never sent. `discardUnsent` refuses a write that was tried before, because the server may have it when the answer got lost. ## Look-back card

- `backend/convex/lookBack.ts` and `lib/lookBack.ts`: `lookBack:get_look_back` returns at most one old item for the viewer's couple, or null. The query reads no clock. The app passes `p_now`, its time rounded down to 15 minutes, and the couple-local date comes from that time and the partners' zones (`resolveCoupleDayAnchorAt`). The result is `{ item, ends_at }`, where `ends_at` is when that couple day ends. Candidates are question rounds both partners answered (`getDailyAnswerDetails` applies the reveal, moderation and deleted rules), visible widget drawings, and visible memories, all at least 7 days old by content date (question: `couple_days.local_date`, drawing: `created_at` in the anchor zone, memory: `memory_date`). Reads are bounded: the newest 60 per source before the cutoff, plus indexed lookups of the same month and day in each of the last 5 years. The question pool is built from both partners' newest answers and keeps only rounds both answered, so it does not depend on who asks. Items from that month and day in an earlier year win. The pick starts at an FNV hash of couple id and date and walks the sorted candidates until one loads, so both partners get the same item all day. Result: `kind`, `content_date`, `on_this_day`, and one of `question` (instance id, both short prompts, `own_answer` and `partner_answer` with a 200-character text excerpt, partner pick, photo and voice flags), `drawing` (revision id, media asset id, author, canvas side) or `memory` (id, title, first visible photo asset id). Media always goes through the existing signed-URL services. Tests in `backend/convex/lookBack.test.ts`.
- `ios/PaeoniaApp/Features/LookBack/`: `Models/LookBackItem.swift` (the result, plus `destination`), `Models/LookBackItem+Display.swift` (what an answer line shows), `Data/LookBackService.swift` (one-shot read), `Data/LookBackCache.swift` (per-user file cache with the couple id, cleared by the privacy purge in `LiveLocalPrivateContentPurger`), `LookBackViewModel.swift`, `HomeLookBackCard.swift` and `LookBackContent.swift` (the card), and `LookBackRefresh.swift` (the Home modifier). Every read runs in a task tied to the Home view, so leaving Home cancels it. A read numbers itself and never applies after a newer one. The cache counts its clears (`purgeCount`), and a read that was in flight during a privacy purge shows and saves nothing. A failed read keeps the item on screen. There is no live subscription, because the content is at least a week old. A drawing hidden by moderation has no local store signal, so it goes away at the next Home appearance. ## Anniversary recap

- `backend/convex/recap.ts` and `lib/recap.ts`: one `anniversary_recaps` row per couple and anniversary. `startRecap` inserts it with a `counting` state, and `countRecapStep` reads whole sources with `.take` while they fit and pages through at most one other source per call (Convex allows one `.paginate` per function), stopping before 1,000 documents, then fills in the all-time numbers, `counted_on` and the moments and removes `counting`. `set_couple_started_on` deletes the couple's recaps when the date changes, and the next open in the window makes a new one. `recapPeriod` runs from the anniversary before, or from the day the couple joined Paeonia when that is later (`since_joined`), up to the day before the newest anniversary, whose own content goes in the next recap, and uses `dateInYear`, so a 29 February start falls on 28 February. A period under 14 days gets no recap. The row holds counts and up to three highlight ids, never content. Every count is something both partners can already see: rounds both answered with visible answers in this couple, visible widget drawings, visible memories and their visible photos, stories not deleted, letters that arrived (delivered or opened, visible, either direction; a sealed letter never counts), visits that overlap the period with their days inside it, a day two visits share counted once, couple days both partners had a game open (`game_play_days`), and the all-time hearts total and longest streak, which the stored data has only as totals. Days together come from planned visits only, because `together_days` keeps 45 days. Memories and visits are paged by fields a person can edit (`memory_date`, `end_date`), so the count keeps their ids and adds each once. While counting, the row keeps the three best-ranked ids per kind by a hash of couple, anniversary and id, and `pickHighlights` takes turns between memories (with a photo first), question rounds and drawings. `recap:get_recaps` returns finished rows without highlights, six per page newest first, with `next_before` for the next page, so a page reads under 20 documents. Hearts are stored per sender in `hearts_sent`, and the API sends their sum. `recap:get_recap_moments` resolves one recap's highlights through `loadLookBackRef` in `lib/lookBack.ts`, the Look Back loaders and rules, so a deleted or hidden moment drops out. `recap:ensure_anniversary_recap` is an action that runs `recap:ensure_step` (one page per call, with the caller's auth) until the newest recap is counted, when the caller's local date is within 14 days of the anniversary. The anniversary branch of the date reminder (`dateReminders.ts`) only schedules `recap:start_recap`, which counts through `recap:count_recap` calls that each schedule the next, so a recap that fails never undoes a reminder. Its push points at `paeonia://recap/<date>` (`recapDeepLink`). A count that stops part way stays unshown and resumes from its cursor on the next ensure. `endRelationshipForPair` deletes the couple's recaps (leaving, blocking, reporting, bans and account deletion), and the relationship cleanup and purge delete them again. The export lists finished recaps as shared, with only the person's own entry of `hearts_sent`. Tests in `backend/convex/recap.test.ts`, `lib/recap.test.ts` and `dateReminders.test.ts`.

- `ios/PaeoniaApp/Features/StreakRestore/Detail/StreakDetailView.swift`: streak detail presentation, with a dimmed flame and "start your streak" copy at zero, the next milestone with its badge row (`StreakMilestoneProgressView.swift`), and a line about the free streak freeze (`CoupleStreak.freezeNote`). - Streak break rules (`backend/convex/lib/streaks.ts`, `streakBreakChange`, `applyCoupleActivity`, `applyStreakRestore`, and `brokenStreakDeadlines` in `streakDeadlines.ts`). A missed couple day that no freeze covers breaks a streak of 3 or more. The next couple day is the free save day: if both partners do something that counts before it ends (`save_deadline`), the streak comes back with that day added and the missed day left out, and `saved_on` records the day. On the second and third couple days after the missed one the paid restore is open (until `restore_deadline`), and a purchase on the save day is refused. After that the old streak is gone. Every window ends at local midnight in each partner's zone, and the latest one wins. A new streak that both start during the restore days keeps the offer open, and a restore adds the new streak's days on top of the old count; without one, the restored streak goes on from yesterday so the couple keeps all of today. The stored break is `isStoredBreak`: `restorable_count` above 0 while the last qualified date is still `restorable_through_date`.
- Together days (`backend/convex/lib/together.ts`). Every date here is on the streak's clock, `StreakClock`: the partners' streak zones (`resolveMemberStreakTimeZone`, the zones the deadline uses). `dayOf` gives the date an instant is on, the earliest local date among them, and `dayEnd` when a date ends, its latest local midnight. A date is a together day when a `together_days` row spans it (`start_date` to `end_date`), or a visit covers it from the visit's `together_from` (the date its dates were last saved). A date that ended keeps what it was: `save_visit` and `delete_visit` call `keepVisitDays` before changing a visit's dates, and a location match stores only today. `update_latest_partner_location` calls `noteLocationFix`. A fix at most an hour old, the partner's latest at most 12 hours old, both accuracies 500 m or better and less than `TOGETHER_RADIUS_METERS` (1000 m, the Lock Screen distance widget's line) apart store the date of the later capture when it is today, once per date (`recordLocationTogetherDay`, which extends a row that ended yesterday). The partner's latest fix counts while the partner shares, paused or not (`sharesLocation` in `lib/locationPause.ts`), as the map still shows it, so a pause changes no together day and no letter the other partner sees. Nothing carries a match to the next day, and nothing changes a stored date. The first `MAX_TOGETHER_PAUSE_DAYS` (14) together days in a row rest the streak. In `lib/streaks.ts`, `restsAfter` finds the days a streak needs after its last qualifying moment, and is null when the five days after it all need both partners. Then every deadline, the freeze and the save and restore offer are the base's own (`notBefore` passes them through). Otherwise each is the base's value or the end of the needed day, whichever is later. A broken streak's save day and restore days are moved on read (`offerNow`, `currentOffer`), and a stored break is never worked out again. A day a paid restore filled in keeps its stored deadline until both act again. The location match does not touch the stored deadline, so `streakReminderDay` stores the moved one in the reminder crons and skips the reminder for the old one, and the reminder key names the moved needed day. `retention.ts` deletes dates 45 days after them. On a resting day `question_time_reminder` is skipped, and `game_turn_reminder` is held a day at a time until the first day apart (`waitsWhileTogether`, `pushQueue.ts`). The streak payload and the Lock Screen payload carry `rest_starts_at` and `rest_ends_at`, the instants the streak starts and stops resting. `CoupleStreak.rest` holds them, so the streak pill (`moon.zzz.fill`), the streak sheet, `HomeVisitCard`'s rest line and the Home Screen streak widget compare the time with them, also from cache, and the Lock Screen timeline adds them as entries. `HomeVisitCardState` reads "Together until" with the last day of the visits in a row that hold today, or "Together today" while the streak rests and no visit holds today. The visit editor keeps dates from 2000 to 2100 and at most 366 days, as `save_visit` does. Scenarios `visit-together`, `visit-ended-yesterday` and `visit-streak-sheet`. Tests: `backend/convex/together.test.ts`, `backend/convex/lib/together.test.ts`, `ios/PaeoniaAppTests/HomeVisitCardStateTests.swift`, the together cases in `CoupleStreakTests` and `LockScreenStatusTests`.
- `ios/PaeoniaApp/Features/DailyPrompt/`: the daily question card. `DailyPromptCard.swift` picks the shape from `DailyPromptCardArt` (pure, with `DailyPromptCardHold`) and plays the seal moment. `DailyPromptHeroCard.swift` is the picture card for loading, no questions yet and active. - `ios/PaeoniaApp/App/MainTabView+TodaysQuestion.swift`: opens today's question by itself when the person opens the app and hasn't answered yet. It opens at most once per couple day, from Home's envelope with the usual zoom, and once more if the partner has answered since it last opened. Opening the answer flow by any route counts, because `openAnswerFlow` records it in `TodaysQuestionOpeningStore` (`Features/DailyChallenge/Challenge/TodaysQuestionOpenings.swift`), and `TodaysQuestionOpening.mayOpen` holds the rule. It acts only on a plain open. A visit starts when the app goes to the background or launches cold, and a push, widget, link, Siri or Spotlight in that visit (`deepLink`, `widgetDrawingPresented`) stops it. It waits until the app is active, the launch intro has ended and the app lock is open. Then the Us tab must be in front with nothing presented over it, or the visit ends without opening. - `ios/PaeoniaApp/Services/Analytics/PaeoniaAnalytics.swift`: usage statistics and crash reports in PostHog (EU Cloud, project 309819, key `PAEONIA_POSTHOG_PROJECT_KEY` in the xcconfig files). There are no screen recordings. Nothing starts until a paired person says yes: `UsageSharingModel` (same folder) keeps each person's answer on the server (`analytics:get_usage_sharing`, `analytics:set_usage_sharing`, fields `shares_usage*` on `profiles`). A yes starts PostHog only after the server saved it, a no stops it at once, and an answer the server has not saved yet stays on the phone and wins over the server's. The answer is read again each time the app comes to the front. `RootView+UsageSharing.swift` follows only the paired person (`usageSharingUserID`), so PostHog never counts screens before pairing. The signed-out welcome steps are counted separately and anonymously by `WelcomeFunnelRecorder` (`Features/Auth/Welcome/`), as daily totals per step on the server. `UsageSharingQuestionView` is the last page of profile setup (`AuthOnboardingView`), so a new account answers before pairing. The switch in Privacy and safety changes the same answer. Screens are counted with `View.analyticsScreen(_:)` where each paired screen is shown. Feature use is counted in one place: `PaeoniaConvexClient` reports the path of every mutation and action that succeeds, and PostHog records it as an event named after the path, such as `memories:create_memory`. Arguments are never sent, and `uncountedFunctions` leaves out background calls and anything about reports, a relationship ending, privacy requests or account deletion. Saying no after a yes, signing out, any other session end (`endSession`) and deleting the account call `stopSharingAndDeleteQueued()`. Before PostHog has started it deletes PostHog's files at once. Otherwise it closes `AnalyticsUploadGate`, a URL protocol on PostHog's session that fails every request, keeps it closed for the rest of the run, and makes the next launch delete PostHog's queue and crash report files, because PostHog's own opt-out still sends what it queued. The server then asks PostHog to delete the person (`delete_analytics_person`, and the account deletion job), and the monthly `delete-inactive-analytics-persons` cron deletes everyone inactive for a year, because PostHog cannot delete events by age. PostHog's setup takes about 90 ms, so every PostHog call runs in order on one background queue (`sdkQueue`) and none runs on the main thread. Archives upload dSYMs in the app target's "Upload dSYMs to PostHog" phase, which runs the SDK's `build-tools/upload-symbols.sh`. Plain builds skip the phase. It declares the app's dSYM as an input, so Xcode runs it after dsymutil.

## Account Lifecycle And Local Privacy

- `ios/PaeoniaApp/App/RootViewModel.swift` (with its `RootViewModel+*.swift` extensions) and `ios/PaeoniaApp/Services/Auth/`: root-owned sign-out/deletion lifecycle, paired profile updates, and access re-resolution. Sign-out first calls `PaeoniaSyncService.flushPendingWrites` (at most 4 seconds) so waiting writes go out while the account can still send, then leaves Clerk and purges whatever is still unsent. `AuthNetworkDeadline` caps the network part of sign-in. - `backend/convex/dataExport.ts`, `dataExportBuild.ts` and `lib/dataExport*.ts`: "Download my data" (GDPR Art. 15 and 20). `lib/dataExportRegistry.ts` lists every table and how it is exported, and `lib/dataExportRegistry.test.ts` fails when a table in `schema.ts` is missing. `request_data_export` queues a job, the Node actions in `dataExportBuild.ts` build zip files (README, JSON per table, the person's original media files), the person gets a push, and signed `GET /data-export` links serve the zips for three days. - `ios/PaeoniaApp/Storage/Privacy/`: centralized, idempotent owner-scoped privacy purge. Temporary entitlement loss hides widget/media/location derivatives while preserving drafts and pending work; permanent relationship loss purges relationship content; sign-out/account deletion remove all owner SwiftData rows, drafts, caches, widget/App Group files, invite credentials, and persisted relationship identifiers.
- `ios/PaeoniaApp/Services/Access/AccessLiveFeed.swift` and `RelationshipEventsLiveFeed.swift`: live subscriptions to `access:get_access_snapshot` and `relationship:get_relationship_sync_events`.   - Backend: `location_sharing_preferences.paused_until` (index `by_paused_until`). `location:update_location_sharing_preference` takes `p_paused_until` (only with `p_is_enabled: true`, at most 48 hours ahead, a time already past is ignored) and keeps the stored location, which only turning sharing off deletes. `update_latest_partner_location` refuses with `42501 location sharing is paused` until the time, and the first update after the time ends the pause itself. ## Siri and App Intents

- `ios/PaeoniaApp/Features/Siri/`: Siri, Apple Intelligence, Shortcuts and Spotlight. The supported Siri actions, content entities and their enums adopt App Intents schemas (`@AppIntent(schema:)`, `@AppEntity(schema:)`, `@AppEnum(schema:)`), for system-defined actions. Custom tools use `@AppIntent(.tool)` with iOS 27.3 availability. The build/test wrappers and `swift-typecheck` source `scripts/lib/paeonia-xcode.sh` to select an installed SDK of 27.3 or newer for that process, without changing the machine default. Intents run in the app process. Schema intents take their titles from the schema. Enum case names are App Intents metadata, so they use manual `siri.*` catalog keys (see `docs/agent-guides/ios-localization.md`). The build checks each type against Xcode's schema list and fails on a missing schema property.
- `Foundation/SiriAccess.swift`: the access gate. `SiriAccess.decide` turns the saved session, the phone's data owner and the cached access snapshot, resolved the way Root resolves it, into `.signedOut`, `.notPaired`, `.noAccess` or `.allowed(SiriCouple)`. `RootViewModel.siriAccess()` reads them without the network. Every intent, entity query, photo export and index pass asks it first, and does nothing without access. Tests: `PaeoniaAppTests/Siri/SiriAccessTests.swift`.
- `Foundation/SiriAppContext.swift`: `SiriAppContext.shared`, connected to the root view model in `PaeoniaApp.init` for the production root only. It gives intents the access, `syncAfterLocalChange`, and navigation through `PaeoniaNotificationRouter`, the same `PaeoniaDeepLink` path as a tapped notification. `AppIntent.coupleToActFor()` gates intents that read or change content. Without access it throws `needsToContinueInForegroundError` with a plain sentence, and the app opens where Root routes. With App Lock on it continues in the foreground and waits up to two minutes for `AppLockModel` to unlock (`activationCount` tells it the lock has decided). `coupleToOpenFor()` gates open and search intents, which open the app anyway, so App Lock's cover hides what they open.
- `Foundation/SiriContent.swift`: builds the entities from the caches the screens read. Dates come from `CoupleDatesViewModel` (the cache with this phone's queued writes laid over it), memories from `loadCachedMemories` grouped by `MemoryTimeline`, which leaves out hidden, removed and pending-delete memories.
- `Foundation/SiriEntityIndexer.swift`: keeps the named Spotlight index `no.paeonia.app.entities` equal to what the person sees. It starts in `PaeoniaApp.init`, so it also runs when an intent launches the app in the background. It follows `LocalStoreChanges` for memories, couple dates, pending operations, access, chat messages and summaries, stories, daily questions and topics. `MainTabView` also asks for a pass when it appears. A pass checks access, rebuilds the entities, deletes the removed ids and indexes the new and changed ones. One pass runs at a time. Each query's `IndexedEntityQuery` reindex methods ask for a full rewrite. The index follows the local caches, so after a new sign-in the memories appear once the Memories feed has run.
- Privacy purge: `LocalPrivacyPurgeService.purgeRecords` calls `SiriEntityIndexClearing.removeAllEntities()` after the record purge, for every scope: sign-out, account deletion, leaving and a temporary loss of access. A failure keeps the purge request queued, and the retry removes the index again. A removal bumps a generation, so an index pass that started earlier never writes after it. Photos from other apps that wait in `MemoryPhotoInbox` go with the other owned drafts. Tests: `PaeoniaAppTests/Siri/SiriIndexPrivacyPurgeTests.swift`. Purge tests pass `FakeSpotlightIndex`, because the real index answers slowly in the unit-test host.
- `Calendar/`: `CoupleCalendarEntity` (`.calendar.calendar`, the one "Our dates" calendar), `CoupleDateEntity` (`.calendar.event`, id `CoupleDateID.countdown(UUID)` or `.birthday(userID:)`, all-day, a yearly `recurrence` for birthdays and yearly countdowns that puts 29 February on 28 February, `nextDate` for the subtitle) and `CoupleDateAttendee`, which the schema requires and Paeonia leaves empty. `CoupleDateIntents.swift`: create adds a countdown, update changes a countdown's title, day or yearly repeat or a birthday's day, delete removes a countdown or a birthday, and open (`.system.open`) opens the dates timeline. Writes go through `CoupleDatesViewModel`, the editors' queued path (`CoupleDateWrites`).
- `Photos/`: `MemoryAlbumEntity` (`.photos.album`, one per memory) and `MemoryPhotoEntity` (`.photos.asset`, id `MemoryPhotoID.saved(mediaAssetID:)`, or `.incoming(UUID)` for a photo from another app, place from the memory). A photo exports as JPEG through `MemoryMediaImageService` and imports from another app into `MemoryPhotoInbox`. `MemoryIntents.swift`: open a memory (`openAlbum`), open a photo (`.system.open`, `PaeoniaDeepLink.memoryPhoto`), `createAssets` (stages the files and opens the new-memory form with them, `PaeoniaDeepLink.newMemory`, since a memory needs a title), rename (`updateAlbum`), `deleteAlbum`, `addAssetsToAlbum`, `removeAssetsFromAlbum` and `deleteAssets`, all through `MemoriesViewModel.saveEdits` and `deleteMemory` (`MemoryWrites`). The photo-editing properties the schema requires stay empty, and Paeonia adopts no photo-editing intents.
- `Messages/`: `ChatPersonEntity`, `ChatConversationEntity` and `ChatMessageEntity` adopt the Messages schemas, `IndexedEntity` and shared ownership. `SiriChats` reads the chat summaries, messages and pending sends through `ThreadChatService`, uses the summary's newest message before a chat is opened, resolves subject titles from the local caches, and includes an empty "Just us" conversation before the first send. Private topic chats (Flirt) and question chats whose privacy is not yet known are excluded from Siri and Spotlight. Message bodies use the schema's `textContent` indexing key. A cached voice message's body is its transcript. Summary-only messages have no transcript until the full message reaches the cache. Send and unsend use the chat service's outbox. Edit, reaction and read status use the same service methods as the chat UI. Edits and unsends re-read the message and apply `canEdit` and `canDelete`. Marking unread returns an explanation because the app has no unread-marking action. Marking read also clears the delivered alerts of the messages it covers, as reading in the chat does.
- `Messages/ChatSendIntents.swift`: the required send/draft group. A partner destination goes to "Just us". The destination union accepts only Paeonia person entities, as one person or a list. Generic Contacts recipients are excluded because their identifiers cannot identify a Paeonia partner. A separate conversation parameter selects another chat. Text and links are supported. Attachments, voice input, subjects and scheduled sends return an explanation rather than losing part of the request. Draft opens the selected chat and appends its text to the composer, preserving any unsent message or photo caption. Delivery waits while a sent message is being edited. `SiriAppContext.messageDraft` holds the text until the composer consumes it, and every privacy purge clears it. The SDK's union macro needs a `nonisolated` type display property under the app's default MainActor isolation.
- `Messages/ChatMessageIntents.swift`: schema edit, unsend and read actions. Reaction is an authenticated custom Siri tool on iOS 27.3. It sets one emoji through `ThreadChatService.setReaction`.
- `Daily/`: custom tools read today's cached/reloaded question, start the shared day through `DailyChallengeViewModel.startToday` when it has no active question, and submit a text answer for that exact instance through `DailyChallengeViewModel.submitAnswer`. Entity lookup and answering never start a replacement day. They refuse rollover, an existing answer or queued send, existing drafts, incompatible answer kinds and excessive text. The active daily model is shared through `SiriAppContext` so unsaved composer text is respected. A background invocation uses the same persisted stores. Success means durable local enqueue, not server delivery.
- Custom Siri tools require the iOS 27.3 Siri AI Developer Preview on an Apple Intelligence device in a supported region. Apple supports development-signed builds and internal TestFlight testers during this preview, not external TestFlight or App Store builds. Existing schema actions keep their earlier availability. Build with `DEVELOPER_DIR=/Applications/Xcode-27.3.0-beta.app/Contents/Developer`; the app's minimum target remains iOS 27.0. See [Apple's preview availability](https://developer.apple.com/documentation/appintents/siri-ai-developer-preview).
- `Messages/PaeoniaChatShortcuts.swift`: publishes app-scoped send, draft, edit, unsend and reaction phrases through `AppShortcutsProvider`. `Resources/Localization/AppShortcuts.xcstrings` supplies English and Bokmal phrases with the system application-name token. App startup calls `updateAppShortcutParameters` to register them. These phrases add explicit routing examples alongside the schema actions; speech recognition still needs device verification.
- Notifications: message pushes already include `thread_id` and `message_id` for every chat kind. The app passes the message id through `PaeoniaForegroundNotice` and annotates its foreground banner with the real `ChatMessageEntity`. The existing communication-notification extension stays unchanged. A trial reference entity in that extension caused AppIntentsTesting to resolve the message through the notification-service extension and fail with `LNConnectionErrorDomain` 1100 because that extension point cannot serve the query. The proxy was removed. Background announcement context therefore remains unavailable; foreground banners and open chat rows provide context inside the app.
- `System/SearchPaeoniaIntent.swift`: `.system.searchInApp` opens Search with the words typed in (`PaeoniaDeepLink.search`, `SearchViewModel.begin(query:)`).
- Onscreen awareness: memory cards (`MemoriesScreen`) and the countdown and birthday rows of the dates timeline (`RelationshipTimelineView`) carry `.appEntityIdentifier`. Chat message rows carry message identifiers, and the open chat publishes its conversation in `NSUserActivity`. The open memory publishes an `NSUserActivity` with the memory's entity, and each photo in its carousel carries its photo's entity (`Photos/MemoryOnScreenForSiri.swift`).
- Every intent that reads or changes content sets `authenticationPolicy = .requiresLocalDeviceAuthentication`. With the Xcode 27.3 SDK, private entities also require local device authentication, and the daily prompt property declares the same policy. These controls protect Siri responses. They do not establish that Spotlight hides indexed text while locked. Full indexing remains enabled. By the developer's decision, both partners' visible memory notes are indexed as text on `MemoryAlbumEntity.searchableAttributes`. Hidden and deleted notes stay out through `visibleBody`.
