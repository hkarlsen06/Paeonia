# Implementation Map

This is the first stop when an agent needs to find the current owner of a Paeonia behavior. Keep this file factual and source-oriented; durable rules still belong in `AGENTS.md`.

## Launch, Root State, And Navigation

- `ios/PaeoniaApp/App/RootView.swift`: root body, top banner mounting, and the cold-launch intro (`LaunchExperienceView`), which stays up until the intro signals it has fully unmasked the app (not just when `state` leaves `.launching`). `RootView+Screens.swift` maps each `AppState` to one screen, and `RootBrandedFrame.swift` holds the brand lockup still over profile setup, the paywall, pairing, and the account-ended screens while only their content crossfades; `RootView+Actions.swift` forwards user actions and reacts to session, state, and invite-code changes (an invite link opened while paired is dropped with a banner); `RootView+System.swift` owns deep links, widget sync, push registration, and the foreground pass (one pass at a time); `RootView+PermissionPrimers.swift` offers the notification primer as Home settles after pairing (it needs no server data) and the location primer after the sharing preference is known, offering at most one primer per visit so the two never appear back to back. The foreground pass refreshes location next to the sync, so content never waits on GPS.
- `ios/PaeoniaApp/App/PaeoniaApp.swift`: builds `RootViewModel` and `LocationMapViewModel` once (after Clerk is configured) and gives the root view model a Clerk session check, so a session that ends while the app runs is noticed.
- `ios/PaeoniaApp/Features/Auth/LaunchExperienceView.swift`: the cold-launch intro that continues the system launch screen. The composed petal mark holds only until `contentReady`. Then the two petal halves (`PaeoniaMarkPetalLeft`/`PaeoniaMarkPetalRight`, split from `PaeoniaMark` on the same viewBox) move apart while a circular hole opens from the center. The hole masks the whole overlay, so it cuts away the petals and the plum canvas together, then grows past the corners to unmask the first app surface. The petals ease out and the hole eases in, so the hole catches them about 120 ms in and the reveal finishes after 600 ms. Reduce Motion fades the overlay instead. No wordmark reveal.
- `ios/PaeoniaApp/Features/Auth/LaunchReveal.swift`: the coordination glue between the intro and the surface it uncovers — `EnvironmentValues.launchContentRevealed` (cues eligible content as the intro exits) and `EnvironmentValues.launchSidesUncovered` (true once the opening hole reaches the screen's sides), and `EnvironmentValues.launchIntroComplete` (true once the intro fully finishes), all set on the routed content in `RootView` and defaulting `true` outside the cold launch, plus reusable entrance modifiers for surfaces that still use a staggered reveal. `PairedHomeView` keeps its Home cards stationary on cold launch so the opening petals remain the focal motion; `CoupleMapCard`'s first flame sweep waits on `launchSidesUncovered` so it plays as the screen opens, not hidden behind the overlay.
- `ios/PaeoniaApp/Features/Auth/AuthBaselineViews.swift`: `AuthLaunchingView`, the quiet, copy-free loading surface shown under the cold-launch intro. Also the deleting-account and relationship-ended screens.
- `ios/PaeoniaApp/Features/Auth/Onboarding/AuthOnboardingView.swift`: profile setup after the first sign-in (name and optional cropped photo). Scrolls, keeps Continue above the keyboard with a loading state, and puts sign out and delete account in quiet links under it. It has no navigation bar, so the lockup above stays at the same height into the paywall.
- `ios/PaeoniaApp/Features/Auth/Welcome/WelcomeView.swift`: the single signed-out screen: brand lockup (same size and place as in `RootBrandedFrame`), a short feature list, and the sign-in controls pinned at the bottom. There is no carousel. "Have an invite code?" opens `PairingCodeEntrySheet`; the code is kept through sign-in and joined on the next screen.
- `ios/PaeoniaApp/Features/Auth/SignInView.swift`: the sign-in controls inside `WelcomeView`: white Continue with Apple, Continue with Google, the invite-code row, and in-app privacy, terms, and support links. Only the tapped provider shows a spinner (`RootViewModel.signingInWith`).
- `ios/PaeoniaApp/App/RootViewModel.swift`: root auth/access/pairing state. `RootRoute.swift` is the route enum; while access resolves after sign-in or profile setup the route holds that screen (with its button spinner) instead of showing an empty one. The selected tab resets to Home whenever the state leaves `.paired`. `RootViewModel+Account.swift` owns sign-in, sign-out, deletion (cancelling the Apple re-sign-in sheet keeps the account), profile saves (success is reported once the profile is saved; sync follows), and sessions that end on their own (back to sign-in with a banner, local data kept). `RootDeviceOwnerStore.swift` remembers whose data is on the phone, so signing in as someone else clears it like a sign-out. Installs from before the marker use the widget's saved identity instead. `RootViewModel+AccessResolution.swift` resolves access; on a slow cold launch it shows a saved paired snapshot after one second. `RootViewModel+Sync.swift` starts sync and stops if the session ended during startup. `RootViewModel+Refresh.swift` re-checks access after a purchase, a renewal, or a pairing change without restoring the session, so a failed check never signs anyone out. `RootViewModel+State.swift` holds the read-only state the views use. `RootPairingCelebrationState.swift` decides when the celebration shows. Tests in `ios/PaeoniaAppTests/RootViewModelFlowTests.swift` and `RootSessionLifecycleTests.swift`.
- `ios/PaeoniaApp/App/RootPrivacyLifecycle.swift`: cold-launch/foreground draining and bounded recovery for durable local privacy-purge retries; blocks a new paired route and sync startup until an older owner-scoped purge has completed.
- `ios/PaeoniaApp/App/MainTabView.swift` and `ios/PaeoniaApp/App/MainTab.swift`: tab layout and high-level feature entry points. `MainTabIdentity` and `MainTabActions` carry the root's data and callbacks; `MainTabModels` builds the tab view models once. `MainTabView+Flows.swift` owns the daily answer covers, streak sheets, and deep links (each link checks it is still current after its refresh). The tabs are Home, Questions, Games, Memories, You.
- `ios/PaeoniaApp/App/DeveloperScenarios/`, `ios/PaeoniaApp/App/RootFeatureDependencies.swift`, and the shared `Scenarios` Xcode scheme: Debug-only deterministic state launcher plus interactive local flows through the production root. It replaces sign-in, StoreKit, Convex, APNs, sync, and persistence boundaries with in-memory dependencies. Use `PAEONIA_SCENARIO=<id>` or `-paeonia-scenario <id>` for direct UI-test launches. The extension contract is in `docs/developer-scenario-harness.md`.
- `ios/PaeoniaApp/App/RootNoticeLocalization.swift`: root-level user-facing notice copy.
- `ios/PaeoniaAppTests/AccessRouteResolverTests.swift`: access route behavior around launch and relationship access.

When a launch-time network call is cancelled with `NSURLErrorCancelled` / `URLError.cancelled` shortly after render, inspect `.task(id:)` keys before hiding the error. The known Daily Challenge case is documented in `AGENTS.md`.

## Daily Challenge

- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeView.swift`: screen composition, loading hooks, and presentation flow.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeViewModel.swift`: screen state, participant refresh, loading, answering, and reveal coordination. `apply` drops the active day once its `endsAt` has passed (`DailyChallengeSnapshot.endingCurrentDay(ifEndedBy:)`, with an injected `now` clock), and a day-end task re-applies that and reloads at the end of the day, so an ended day never shows as today, even offline. `submitAnswer` refuses your own answer after its day ended (`Notice.dayEnded`, draft kept) and any text over `DailyAnswerDraft.maxTextLength` (2,000 code points, the backend limit), because the server would reject both and the outbox would retry forever. `isSending` turns false as soon as the snapshot carries the sent answer. `refreshSendingState` runs on every live apply and on `.pendingOperations` changes, and skips a store read that started before a newer local send (`sendingGeneration`). On outbox changes it also picks up answers the outbox put back into the drafts and raises `Notice.submitFailed`. Skip is gated on `hasDraftContent` (anything typed or staged), not on whether the draft can be sent. Photos are compressed off the main actor in `stagePhoto` with a per-question token, so a removal, skip, or newer pick wins, and Send waits for the photo. `shuffle` also deletes the skipped question's staged media. `applyRestoredStreak` shows a bought-back streak before the server refresh confirms it.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeStepBar.swift`: step/progress UI for the main challenge flow. The flow passes the answered steps by position (`completedSteps`), since the user can answer the second question first; the Home card passes a count. Tappable segments have a padded hit area and a VoiceOver adjustable action.
- `ios/PaeoniaApp/Features/DailyChallenge/Challenge/DailyChallengeNoticeLocalization.swift`: localized title/message mapping for `DailyChallengeViewModel.Notice`.
- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeModels.swift`: UI/domain models and answer-kind shape.
- `ios/PaeoniaApp/Features/DailyChallenge/Models/DailyChallengeRemoteRows.swift`: DTOs matching the `backend/convex/daily.ts` function results.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeService.swift`: Convex calls for challenge/day/question/answer behavior.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeDraftStore.swift`: local answer draft persistence.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeSnapshotCache.swift`: local-first cold-launch cache. The live service writes the raw `DailyChallengeRemoteSnapshotRow` (keyed per user) on every successful snapshot load; `DailyChallengeViewModel.configure` seeds `snapshot`+`streak` from it via `DailyChallengeRemoteSnapshotRow.loadResult` before the network `reload()`, so returning users see real content (not placeholders) on the first frame. The centralized local privacy purger clears it on relationship access loss or user departure.
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengeLiveFeed.swift`: live feed for today's challenge. It follows `daily:get_daily_challenge_snapshot` for the known couple day, or `get_today_daily_challenge_snapshot` when no day exists yet. Every today subscription (and every one-shot `loadTodaySnapshot`) uses a fresh random `p_day_key`, because the couple day ends at the westmost partner's midnight, not this phone's, so a per-local-date key could be served a stale result. Without a day the today subscription is renewed every half hour or at local midnight. Each result goes into the snapshot cache through `DailyChallengeLiveWriteClock` and posts `LocalStoreDomain.dailyChallenge`; `DailyChallengeViewModel` re-reads the cache and applies it. It never starts a day.
- `ios/PaeoniaApp/Features/DailyChallenge/Chat/Data/DailyQuestionChatLiveFeed.swift`: live feed for `threads:get_conversation_threads` summaries (posts `LocalStoreDomain.dailyChat`). An open chat follows `threads:get_thread_messages` through `DailyQuestionChatServicing.liveMessageUpdates`, which merges each result into `FileDailyQuestionChatCache` and links server copies of still-sending messages to their operations (`DailyQuestionChatMessage.claimingPending`).
- `ios/PaeoniaApp/Features/DailyChallenge/Data/DailyChallengePendingOperationHandler.swift`: local-first retry handling for queued challenge writes. A submit the server refuses for good (`23514`, `23505`, `22023`) becomes a terminal failure and the answer goes back into the drafts (`DailySubmitAnswerOperationPayload.Content.restoredDraft`), which `DailyChallengeViewModel` picks up when the drain posts `.pendingOperations`. Upload errors and access errors (`42501`) keep retrying. `DailyChallengeLiveWriteClock.notePurge()` (called from the snapshot cache's `clearAll`) stops a response that was in flight during a privacy purge from writing the couple's content back.
- `ios/PaeoniaApp/Features/DailyChallenge/Chat/`: each answered question's own page (`DailyQuestionChatView`) and view model, thread/message RPC service, owner-scoped local cache, optimistic merge rules, and pending-operation handlers for lazy thread creation and sends. The chat copies Tidex's friends chat (`~/repo/Tidex/ios/TidexApp/Features/Friends/Messages/`) on the same `hkarlsen06/Chat` fork commit: `.animateMessageUpdates(false)`, a custom composer through `inputViewBuilder`, a zero-height `betweenListAndInputViewBuilder`, day dividers, and the long-press menu (`Thread/DailyChatMenuAction`). `Thread/DailyChatProjection` builds ExyteChat's messages and the row models once per data change and folds everything a row draws into `triggerRedraw`, so ExyteChat redraws only rows that changed. `Thread/DailyChatMessageRow` draws Paeonia's question (logo avatar), the answers, and messages, with grouped bubble corners, quotes above replies, voice messages, and a Sending / Sent / Not sent line. `Thread/DailyChatGestures` and `Thread/DailyChatGestureBridges` are the Tidex swipe gestures: swipe a bubble toward the middle to reply, swipe left to show times, swipe right to go back. `Thread/DailyChatComposer` is the text field and reply banner, and its microphone records with `DailyVoiceRecorder` (the voice-answer recorder). Replies send `p_reply_to_message_id` to `threads:send_thread_message`, and the long-press menu reports a partner message as a `thread_message` target. Typing dots and read receipts use Tidex's timings in `DailyChatPresenceModel`: a typing heartbeat at most every 2.5 s through `chatPresence:set_daily_chat_typing`, a stop after 4 s idle or on send, and the partner's dots hidden 5 s after their last heartbeat or 2 s after a stop. `chatPresence:get_daily_chat_presence` is one live query for the partner's typing time and read mark. Typing is keyed by the question instance so it works before the thread exists. Reading is marked with `chatPresence:mark_thread_read` 200 ms after the newest message shows while the chat is on screen. The projection puts Read on your newest message the partner has read through and Sent on your newest message. Photos: up to 4 per message from the composer's drawer (`Thread/DailyChatComposerAttachments`), compressed when picked with `ImageCompressor`, uploaded with the `thread_media` purpose under the message's id, and shown at fixed sizes by `Thread/DailyChatPhotoViews`. Tapping one opens every chat photo in `PaeoniaImageViewer`. `threads:get_thread_messages` returns `media` with each attachment's type and size, and `get_conversation_threads` returns `last_message_media_type` for the preview. The chat opens at the question while nobody has written yet, and at the newest message after that. Callers await `DailyChallengeViewModel.prepareChat(for:)` before pushing it, and the Questions screen hides the tab bar before the push. `PaeoniaImageMemoryCache` keeps decoded avatars and answer photos in memory so rebuilt rows don't flash placeholders. The privacy cleanup empties it with the disk caches. Until both answers are revealed the page shows the question and answers and who it waits for, with no composer. Voice messages: the queued operation carries the .m4a bytes, and the send handlers upload them through `LiveDailyAnswerMediaUploadService` with the `thread_message_media` parent before sending. The server gives the message the id the upload was reserved under, which is how the server copy is matched to the pending one. Unread state is kept only on this phone. The cache stores when the user last saw each thread (`readThroughByThreadID`), and an open chat moves that mark forward. A chat is unread when its newest message is from the partner and is newer than the mark (`DailyQuestionThreadSummary.isUnread`). `DailyChallengeViewModel.unreadChats` drives the Questions tab badge, the Home `HomeUnreadChatsCard`, and the unread border on question rows. A fresh install shows every chat whose last message is from the partner as unread.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/DailyChallengeQuestionViews.swift`: reusable question and answer UI pieces.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/DailyQuestionCard.swift`: the question card on the answer and reveal screens. In the answer flows it takes all the height the composer leaves and holds the answer-type picker (or icons) at the top and the "answer to see their reply" note at the bottom. The question text shrinks to fit when the keyboard is up.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/DailyChallengeMediaViews.swift`: image/media display for answers.
- `ios/PaeoniaApp/Features/DailyChallenge/Components/DailyChallengeReadCard.swift`: the shared question row (prompt, who has answered, a status line), used by the Questions tab's single list and the history flow. Rows hold no answers. An answered row opens the question's page, and a partner question the user can still answer opens the answer flow. `DailyChallengeQuestion.list` (in `DailyChallengeModels.swift`) is the shared row→question mapping behind both today's snapshot and history. The Questions tab shows the partner's and the user's questions in one list (`DailyChallengeSnapshot.readOverviewQuestions`), not split into "their"/"mine" sections.
- `ios/PaeoniaApp/Features/DailyChallenge/AnswerFlow/DailyChallengeAnswerFlow.swift`: the multi-question answering flow (step bar, Send/Save/Next, skip, partner reveal, completion hand-off). When there are no questions (start failed or the day ended mid-flow) it offers Start questions instead of only closing. `DailyChallengeAnswerStep.swift` holds one question's prompt and text/photo/voice/partner-choice composers (shared with the partner flow), `DailyChallengeAnswerActionBar.swift` the fixed bottom bar, `DailyChallengeCompletionView.swift` the streak screen with in-place restore (errors shown inline, since the banner sits under the cover), and `DailyFlowPresentation.swift` the zoom-source ids and helpers.
- `ios/PaeoniaApp/Features/DailyChallenge/AnswerFlow/DailyPartnerAnswerFlow.swift`: answering one partner-authored question. On send it holds briefly (`awaitAnswerReveal`), prepares the chat (`prepareChat(for:)`), and then always turns the cover into the question's `DailyQuestionChatView` inside its own navigation stack, with a close button and the report screen. The chat opens with `revealsPartnerAnswer`, so the partner's answer row lights up with the reveal haptic when it first shows, and the keyboard stays down. If the reply is not viewable yet (slow or offline send), the chat's waiting page shows the user's answer, drawn from `sendingAnswer` (`Thread/DailyChatSendingAnswerRow`) until this phone has it, and opens up when the live snapshot unlocks the reply. The chat keeps its own copy of the question if a day rollover drops it from today's snapshot. Swiping right in the chat closes the cover through `onClose`. If the server refuses the answer for good, both flows go back to the question with the answer filled in again. The main flow (`DailyChallengeAnswerFlow`) keeps `DailyPartnerAnswerRevealView` for partner questions, so the remaining questions aren't interrupted.
- `ios/PaeoniaApp/Features/DailyChallenge/AnswerFlow/DailyChallengeCameraPicker.swift`: camera/photo picker used by the answer flow.
- `ios/PaeoniaApp/Features/DailyChallenge/History/DailyChallengeHistory.swift`: pure date-grouping for the history overview (`DailyChallengeHistoryDay`, newest-day-first grouping, local-date parsing).
- `ios/PaeoniaApp/Features/DailyChallenge/History/DailyChallengeHistoryViewModel.swift`: history load/state/readiness, banner-routed reload errors. Loads are numbered so a slower, older load never overwrites a newer result. `ViewState.content` carries `Content { pendingPartnerQuestions, days }`; the partner's still-unanswered questions are read live from the daily-challenge snapshot (`answerablePartnerQuestions`, injected via the `pendingPartnerQuestions` closure from `DailyChallengeViewModel.makeHistoryViewModel()`), refreshed without refetching history by `refreshPendingPartnerQuestions()`, and deduped against the loaded history.
- `ios/PaeoniaApp/Features/DailyChallenge/History/DailyChallengeHistoryView.swift`: the History full-screen cover — title, close, a top "waiting for you" section of answerable partner cards (same CTA as the Questions tab, gated by `hasCompletedRequiredDailyQuestions`, zooms into `DailyPartnerAnswerFlow` and reloads on close), then centered date dividers + read cards, plus empty/loading/error states. Needs the shared `DailyChallengeViewModel`. Opened from the Questions-tab toolbar History button in `DailyChallengeView.swift`.
- `ios/PaeoniaApp/Features/DailyChallenge/Audio/DailyVoiceAnswerViews.swift`, `DailyVoiceRecorder.swift`, and `DailyVoiceAudioSession.swift`: voice recording/playback UI and audio session handling. The recorder has a `.starting` phase so a double tap starts one recorder, discards takes under one second (`isUsableTake`), and hands a partial take to the composer when the view goes away mid-recording. One clip plays at a time, playback loads from bytes (duration known at once) with a retry on failure, and the session is released with `notifyOthersOnDeactivation` so other audio resumes.
- `ios/PaeoniaApp/Features/DailyChallenge/Streak/CoupleStreak.swift`: couple streak calculation and state.
- `ios/PaeoniaApp/Features/DailyChallenge/Streak/StreakMilestones.swift`: which streak lengths are milestones (3, 7, 14, 30, 50, 100, 200, 365, 500, then every year), the streak sheet's badge row, and `StreakMilestoneTracker`, which decides when a phone celebrates one. `StreakMilestoneStore.swift` keeps the shown milestones per user in UserDefaults. The app does this without the server.
- `ios/PaeoniaApp/Services/Media/DailyAnswerMediaDraftStore.swift`, `DailyAnswerMediaUploadService.swift`, and `DailyAnswerMediaImageService.swift`: photo/voice draft storage, upload, and display support. Revealed media is cached in Caches (not backed up) and removed on purge. A failed photo download can be retried by tapping it.
- `ios/PaeoniaAppTests/DailyChallengeTests.swift`: main regression suite for question state, answer flow, reveal behavior, cancellation, and media handling. `DailyChallengeDayBoundaryAndSendingTests` covers ended days, the text limit, sending-state races, photo staging, and refused answers. `DailyChallengeHistoryViewModelTests.swift` covers overlapping history loads, and `DailyVoiceTakeTests.swift` the minimum voice length.

Question content is authored in `backend/questions/`; read `docs/couple-question-guidelines.md` before changing prompts. For combined `text` + `photo` or `text` + `partner_choice` questions, both composers can be shown at once and each part is optional.

Questions history reads through `daily:get_daily_questions_history` and `daily:get_daily_answer_history_details` in `backend/convex/daily.ts`. Both are scoped to instances the viewer has answered and reuse the per-answer reveal rules.

A daily question belongs to the couple-local day of its *latest* answer, not its seed day (`backend/convex/daily.ts`). `get_daily_questions_history` returns `effective_local_date` (the latest answer's date in the couple's anchor timezone) and `DailyChallengeHistory.grouped` buckets on it; `get_today_daily_challenge_snapshot` keeps a carried-over instance in the Questions tab while its latest answer falls on the current couple-local date, so answering a partner's carried question doesn't make it vanish until the next day. The Questions tab is one list (`DailyChallengeSnapshot.readOverviewQuestions`) sorted by `questionsTabOrder`: a partner question still awaiting the user's answer (`DailyChallengeQuestion.isAwaitingCurrentUserAnswer`) is pinned on top, then a card with something new from the partner (`readOverviewQuestions(isNew:)`, fed by `DailyChallengeViewModel.hasNewFromPartner`: an unread chat, or a partner answer the user can read but hasn't seen, per `DailyChallengeQuestion.hasNewPartnerAnswer`). Seen answers are stored on the server (`daily_answer_seen_states`, written by `chatPresence:mark_daily_answer_seen` and returned on question rows as `partner_answer_seen_at` and `own_answer_seen_by_partner_at`) and on this phone in the chat cache, which counts before the server answers. Opening the question page (including the chat the partner answer flow turns into) or the main answer flow's reveal marks the answer seen on this phone. `DailyChallengeViewModel.uploadSeenPartnerAnswers` sends those marks to the server and tries again on the next update if a send fails. The question page shows Read on the user's own answer once the partner has seen it. Chat unread marks also follow the server: `get_conversation_threads` returns `viewer_read_through_at`, so reading a chat on one device clears it on the others. After that comes everything else by `readOverviewOrder` (most recent answer first, via `DailyChallengeQuestion.latestAnswerDate`). The history's within-day order uses `readOverviewOrder` directly. The tab no longer freezes the order or scrolls-to/highlights after answering — answering a partner question opens the question's chat inside the cover (`DailyPartnerAnswerFlow`), so it's fine that the card then re-sorts down into the timeline.

## Memories

- `ios/PaeoniaApp/Features/Memories/Timeline/MemoriesScreen.swift`: the Memories tab. It shows a local-first timeline of memory cards in month sections with pinned headers (one grid of cards without month sections on an iPad in landscape, via `paeoniaWideLayout`), an empty state, a toolbar `+` to create, pull-to-refresh, and push navigation to detail. Notices go to the top banner. It owns its `MemoriesViewModel` as `@State` and configures it in `.task(id: currentUserID)` (load-bearing key). The active couple id flows through `.onChange`, so it never cancels a load.
- `ios/PaeoniaApp/Features/Memories/Timeline/MemoriesViewModel.swift`: `@MainActor @Observable` screen state and all mutations: `createMemory`, `saveEdits` (title/date, own note, removed and added photos), `deleteMemory`, and `savePhotoToLibrary`. `isSaving` refuses a second save while one runs, so a double tap or reopening the form mid-upload can't create a duplicate. `saveEdits` compares with the record as the form opened, so a title or date the person didn't touch keeps the partner's newer value. Photos uploaded by a failed save are reused if the person retries within five minutes (`Data/MemoryPhotoUploads.swift`). The same photo picked twice is uploaded twice, because the server refuses one upload twice in a memory. Each `load` carries a generation, so a slow read can't overwrite a newer one. It talks only to `MemoryDataServicing`, never the repository or the gateway. After each local change it flushes through an injected sync handler (wired to `RootViewModel.syncAfterLocalChange` via `MainTabActions.syncAfterLocalChange`) and reloads the cache. `MemoriesNotice.swift` holds the banner copy.
- `ios/PaeoniaApp/Features/Memories/Timeline/MemoryTimeline.swift`: pure grouping and date helpers, unit-tested. It groups by day (newest day first, newest-created first within a day) and folds days into month sections. It drops hidden, removed, and pending-delete memories. `localDateString(for:timeZone:)` always writes a Gregorian `yyyy-MM-dd`. `pickerDate(forLocalDate:timeZone:)` seeds date pickers at local noon. Never seed a picker with `parseLocalDate`, which is UTC midnight and only for display.
- `ios/PaeoniaApp/Features/Memories/Timeline/MemoryCardView.swift`: one memory's timeline card (date, title, photo strip, note preview, subtle "saved on this phone" while dirty). VoiceOver reads the photo strip as a photo count. `MemoryDateStyle` holds the shared UTC date format styles.
- `ios/PaeoniaApp/Features/Memories/Editor/MemoryEditorView.swift`: the memory form sheet for create and edit. Title and date are required, the date can't be in the future, and a new memory also needs a note or a photo. A new memory's draft (`MemoryDraft.swift`) lives in the view model and on disk via `Data/MemoryDraftStore.swift`, so a swipe-down keeps it. An edit with changes can't be swiped away, and Cancel asks before discarding. The form shows its own copy of the top banner because the sheet covers the root one. The save button shows which photo is uploading. `Components/MemoryTextField.swift` is the shared styled field.
- `ios/PaeoniaApp/Features/Memories/Detail/MemoryDetailView.swift`: the full memory. It shows the photo carousel (tap for the full-resolution viewer, long-press to save to Photos), both partners' notes, an "Add your note" shortcut, edit, and delete (centered confirmation alert). It re-reads its record by id from the view model, so it reflects edits and dismisses itself once the memory is deleted.
- `ios/PaeoniaApp/Features/Memories/Components/MemoryMediaImageView.swift`: shows a memory photo. Bytes come from the shared `MemoryMediaImageService` (signed `get_media_signed_url` download, on-disk cache keyed by media asset id, separate `MemoryMedia` cache dir). `MemoryImageDecoding.swift` downsamples off the main actor and keeps decoded images in memory, so scrolling never decodes full photos on the main thread. A failed photo retries on tap. `MemoryStagedPhotoThumbnail.swift` does the same for photos picked in the form. The centralized local privacy purger cancels in-flight downloads and clears derived media when access is hidden. Permanent relationship loss or user departure also removes owner-scoped local memory rows and pending writes.
- `ios/PaeoniaApp/Services/Memories/MemoryPendingOperationHandlers.swift` and `MemoryPendingOperationResolution.swift`: outbox handlers for memory writes. A revision conflict is rebased on the server copy and sent again. A field the queued edit didn't change keeps the server's value (`UpdateMemoryOperationPayload.baseTitle`/`baseMemoryDate`), and a delete wins. A title/date or note edit waits while an older edit of the same memory is still waiting to retry, so the older one can't land last. A write the server refuses because the memory is gone shows the deletion locally and stops retrying. Other failures retry. Records are never left in the `conflict` state, which would stop them taking server updates. `MemoryDataService.updateMemory` refuses an expected revision that no longer matches the stored record (`staleRevision`), and the view model recomputes the edit from the newer record.
- `ios/PaeoniaAppTests/Memories/`: `MemoryDataLayerTests.swift` (repository and data service), `MemoryPendingOperationHandlerTests.swift` (conflict rebase and deleted-memory handling), `MemoryTimelineTests.swift` (grouping, month sections, date round-trips across time zones and calendars), `MemoriesViewModelTests.swift` (create, edit, delete, drafts, double-save, upload reuse, stale reads, partner edits and deletes), `MemoryLiveFeedTests.swift`, and `MemoryDraftStoreTests.swift`.

Memory photos require an online upload at save time: `MemoryMediaUploading` reserves/uploads/finalizes and returns a real `mediaAssetID`, which the create/attach calls embed as optimistic media. Note-only memories are fully offline/local-first. If any photo upload fails, nothing is saved and the form stays put. Content is never partially dropped. Notes can be changed but not removed, because the backend has no note delete. The form says so instead of keeping the old note silently. Memory thread messages (`createMemoryThreadMessage`) are write-only in the data layer (the snapshot exposes only `threadID`, no message read model), so there is intentionally no thread/conversation UI yet.

## Account Lifecycle And Local Privacy

- `ios/PaeoniaApp/App/RootViewModel.swift` (with its `RootViewModel+*.swift` extensions) and `ios/PaeoniaApp/Services/Auth/`: root-owned sign-out/deletion lifecycle, paired profile updates, and access re-resolution. Sign-out first calls `PaeoniaSyncService.flushPendingWrites` (at most 4 seconds) so waiting writes go out while the account can still send, then leaves Clerk and purges whatever is still unsent. `AuthNetworkDeadline` caps the network part of sign-in. Clerk sign-in plus the first profile load get 30 seconds (Google's sheet is not counted), and the profile load at launch gets 15 seconds before the cached profile opens the app. `AppleSignInService` ends an earlier Apple attempt that never reported back as cancelled when a new one starts, or when its caller is cancelled, so a new attempt always starts. Account deletion obtains a fresh Apple authorization code when possible. Cancelling that Apple sheet keeps the account; any other Apple failure still deletes and shows the manual-revocation step.
- `backend/convex/accountDeletion.ts` and `backend/convex/lib/accountDeletion.ts`: atomic Paeonia-data deletion boundary, relationship ending, device/location/notification cleanup, profile anonymization, retryable deletion jobs drained by a cron, and operator retry functions. `identity:delete_account` is the app-callable action.
- `backend/convex/lib/accountDeletionProviders.ts`: outbound calls for account deletion, Clerk user deletion and Sign in with Apple token revocation. Required environment variables are listed in `backend/AGENTS.md`.
- `ios/PaeoniaApp/Storage/Privacy/`: centralized, idempotent owner-scoped privacy purge. Temporary entitlement loss hides widget/media/location derivatives while preserving drafts and pending work; permanent relationship loss purges relationship content; sign-out/account deletion remove all owner SwiftData rows, drafts, caches, widget/App Group files, invite credentials, and persisted relationship identifiers.
- `ios/PaeoniaApp/Services/Access/AccessLiveFeed.swift` and `RelationshipEventsLiveFeed.swift`: live subscriptions to `access:get_access_snapshot` and `relationship:get_relationship_sync_events`. The access feed writes the snapshot store (skipping identical snapshots), and `RootViewModel` observes `LocalStoreChanges` for `.access` and re-routes: partner accepts an invite, partner leaves or blocks, entitlement changes, and partner name, photo, or start date edits. The events feed saves events, applies them, and persists its cursor only after the apply succeeds, then resubscribes from the new cursor. Root's own purge pauses every feed and runs quiesced, so it also removes anything a stale couple subscription wrote in the meantime.
- `ios/PaeoniaApp/Services/Sync/Streams/RelationshipSyncEventApplier.swift`: maps backend `local_purge_scope` hints to temporary-hide or permanent-purge behavior, treating relationship-end `pending_uploads: review` as permanent for MVP because no recovery UI exists. ## Widget Drawing

- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/WidgetDrawingView.swift`: drawing screen composition. The canvas sits on top; tools, colors, size, and the Clear and Send buttons sit below it. Status lives in fixed-height rows so the canvas never resizes.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/WidgetDrawingCanvasHeader.swift`: the row above the canvas that names who drew the drawing on the widgets, and shows "Not sent yet" or that the partner just sent a drawing.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/WidgetDrawingViewModel.swift`: drawing state, send status (`Delivery`: sending, sent, waiting for the network), loading and partner updates, drafts, and canvas-size scaling. A partner's drawing never replaces unsent strokes or a stroke in progress; the header says the partner sent one instead.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/WidgetDrawingTools.swift` and `WidgetDrawingContent.swift`: tool and color palette types; the stroke content signature, the server's size limits, and scaling a drawing to another canvas size.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/WidgetDrawingControlsView.swift`: color, size, and tool controls, all with 44 point tap targets.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/PencilKitCanvasView.swift`: SwiftUI bridge for PencilKit canvas. It pushes a drawing into PencilKit only when the view model's `drawingRevision` changes, and reports stroke begin and end. Its canvas has no undo manager, so PencilKit keeps no undo stack. While the paint bucket is picked, drawing is off and a tap reports where to fill.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/DrawingEditHistory.swift`: undo and redo for the widget canvas and the Draw & Guess board. Each step keeps only the strokes it changed, so undo leaves the partner's live strokes in place. Clear, the fill, and the widget screen's "go back to the sent drawing" button are steps too. Loading another drawing starts the history over, and a resize scales it.
- `ios/PaeoniaApp/Features/WidgetDrawing/Canvas/DrawingFloodFill.swift`: the paint bucket. It renders the drawing at up to 2 pixels per point and at most 1,000 pixels a side, flood fills from the tap with plain loops over raw memory (debug builds took seconds otherwise), and returns one wide monoline stroke clipped by a mask to the filled area, so a fill saves, syncs, erases, and replays like any stroke.
- `ios/PaeoniaApp/Features/WidgetDrawing/Components/HomeWidgetPreview.swift`: in-app widget preview.
- `ios/PaeoniaApp/Features/WidgetDrawing/History/WidgetDrawingHistoryView.swift` and `WidgetDrawingHistoryViewModel.swift`: preserved drawing history, with retry for a thumbnail or an older page that failed to load.
- `ios/PaeoniaApp/Services/Widget/WidgetCanvasUploadService.swift` and `WidgetPendingUploadStore.swift`: one shared uploader (`WidgetCanvasUploadServiceFactory.shared`) used by the drawing screen and the sync's retry. Uploads run one at a time and a queued upload whose drawing was replaced is skipped. A drawing is marked as not sent before it is shown locally.
- `ios/PaeoniaApp/Services/Widget/WidgetCanvasSyncService.swift` and `WidgetCanvasLiveFeed.swift`: pull the partner's drawing. The sync re-checks for an unsent local drawing right before it applies a download, and the live feed also triggers a sync (and so a retry) when a drawing is waiting to be sent.
- `ios/PaeoniaApp/Services/Widget/WidgetDrawingRasterizer.swift`: raster output for widget payloads.
- `ios/PaeoniaApp/Services/Widget/WidgetSharePayload.swift`, `WidgetCanvasService.swift`, and `ios/PaeoniaWidget/PaeoniaWidgetStore.swift`: App Group payload contract and renderer. Payloads default to redacted; only a current-version validated save opts into drawing display, and malformed/redacted/unsafe-path/undecodable content falls back to the neutral placeholder. Payloads record the canvas side and, for synced drawings, the server revision ID. A privacy hide or clear bumps `paeonia.widget.privacyEpoch` in the App Group defaults before deleting files. MVP supports Home Screen widget families only; the drawing and author are `.privacySensitive()` for StandBy on a locked phone.
- `ios/PaeoniaWidget/PaeoniaWidgetTimelineProvider.swift` and `PaeoniaWidgetRefreshService.swift`: every timeline reload (including widget pushes) first runs a deduplicated HTTP refresh, bounded to 15 seconds, so the partner's drawing appears when the app is not running. The refresh skips a revision already on disk, gives up if the privacy epoch changed or the user signed out, never overwrites an unsent local drawing, and removes the widget files on access-denied (`42501`). Previews live in `Widget/previews`, the same folder the app purges.
- `ios/PaeoniaAppTests/WidgetDrawingViewModelTests.swift`, `WidgetDrawingSendFlowTests.swift`, `WidgetDrawingHistoryViewModelTests.swift`, `WidgetDrawingHistoryLoadingTests.swift`, `WidgetCanvasServiceTests.swift`, `WidgetCanvasSyncServiceTests.swift`, and `WidgetCanvasUploadServiceTests.swift`: focused widget drawing coverage.

MVP drawing payloads are PencilKit-based. Do not replace them with hand-rolled stroke formats unless the product decision changes in `docs/phase-3-data-contract.md`.

## Sync, Access, And Location

- `ios/PaeoniaApp/Services/Sync/PaeoniaSyncService.swift` and `PaeoniaSyncServiceDefaults.swift`: orchestration for local-first sync work.
- `ios/PaeoniaApp/Services/Sync/SyncClientOperation.swift` and `SyncTypes.swift`: queued operation envelope and shared sync types.
- `ios/PaeoniaApp/Services/Sync/Streams/`: the pending operation drain (the offline write outbox) and the relationship event applier. Remote reads no longer poll. Each sync run sends every waiting write, oldest first and at most once per run, including writes still waiting out their retry delay. The delay (1 minute doubling to 5) only sets when the retry timer fires next. A write this build has no handler for stays queued without blocking the writes behind it. Writes the server accepted are deleted at the start of the next run.
- `ios/PaeoniaApp/Services/Live/`: Convex live subscriptions. `LiveQueryService` subscribes, `LiveSyncCoordinator` starts and stops feeds with the session, `LiveFeedRegistry` lists every feed, and `LiveConvexConnection` owns the ConvexMobile client and hands it to feeds only while the socket is logged in as the account signed in to Clerk now. Overlapping `start` calls resolve to the newest session. Each feature's feed (`AccessLiveFeed`, `RelationshipEventsLiveFeed`, `MemoryLiveFeed`, `LocationVisibilityLiveFeed`, `WidgetCanvasLiveFeed`, `DailyChallengeLiveFeed`, `DailyQuestionChatLiveFeed`, `GamesOverviewLiveFeed`, `DrawAndGuessLiveFeed`) writes into the local store, and view models re-read on `Storage/LocalStoreChanges.swift`. `ScreenLiveUpdates` covers data only shown on one open screen.
- `ios/PaeoniaApp/Services/Access/AccessRouteService.swift`, `AccessRoute.swift`, `AccessGateway.swift`, and `AccessDTOs.swift`: current relationship/access routing.
- `ios/PaeoniaApp/Services/Location/`: foreground location capture, gateway, models, and pending operation handling. Concurrent capture requests share one fix. Location uploads the server rejects for good (`42501`, `23514`) stop retrying. `LocationUpdateController` runs the automatic feeds. While the app is open, a live feed reports 250 m moves to `LocationMapViewModel.submitObservedLocation`, which applies the same throttle as app open. While the app is closed, it uses the significant-change service, but only when the person turned on the device-local "Share while Paeonia is closed" switch and allowed Always. `BackgroundLocationUploader` then sends the position directly, since the outbox only runs while the app is open. `PaeoniaAppDelegate` re-arms it at every launch, `RootView+System.swift` feeds it identity, sharing, and scene phase, and the privacy purge resets it.
- `ios/PaeoniaApp/Features/Location/Map/LocationMapViewModel.swift` and `LocationMapStateResolver.swift`: map state. `CoupleMapState` names each card state (sharing off, finding you, no fix yet, iOS location access off, partner not sharing, partner sharing without a location yet, ended, unavailable, ready). Turning sharing off always wins over a refresh that waits for GPS, and the replaced refresh writes nothing. iOS permission is a stored, observable value refreshed on scene activation. Automatic refreshes on app open never raise an error banner, and declining the system prompt is not treated as an error.
- `ios/PaeoniaApp/Features/Location/Map/CoupleMapCard.swift` (card and state switch), `MapEmptyState.swift`, `CoupleMapSnapshot.swift` (snapshot rendering, retries, and the flame reveal), `CoupleMapFraming.swift`, `MapRevealSweep.swift`, `MapAvatarPin.swift` (markers and the recorded-time line), `MapKissLayer.swift` (hearts, paused while none is in flight), and `LocationNoticeLocalization.swift`: map card UI and user-facing state. The permission action first explains latest-location-only, no-history behavior, and that updates happen while the app is in use. The map shows the partner's location age in its top corner ("Just now", "3 min"), and VoiceOver reads the full sentence. Last-known locations do not expire. After 24 hours the partner marker dims and VoiceOver says the location may have changed.
- `ios/PaeoniaAppTests/Sync/` and `ios/PaeoniaAppTests/Live/`: sync coordinator, local store, operation drain, live feed, and coordinator tests.
- `ios/PaeoniaAppTests/Location/LocationFeatureTests.swift`, `LocationLiveTests.swift`, `LocationSharingFlowTests.swift`, and `LocationUpdatesTests.swift`: partner location and visibility behavior, sharing choices racing a GPS fix, permission changes, map card states, the live feed throttle, and closed-app uploads.

Do not discard a last-known partner location merely because it is old. Current product intent is latest partner location only, updates while the app is open plus an opt-in for updates while closed, no location history, a visible 24-hour stale treatment, and a map that appears only after both partners opt in.
