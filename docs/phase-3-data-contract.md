# Phase 3 Data Contract

This document captures product and data-model decisions before writing Supabase migrations.

The goal is to make backend behavior explicit before schema, RLS, local sync, and UI flows start depending on hidden assumptions.

## Status

This is a decision document, not a generated migration file.

Migrations should still be created with the Supabase CLI when implementation starts, but the migration-critical product and schema decisions are expected to live here first.

## Schema Principles

Use relational modeling wherever the app needs to enforce ownership, query data, secure rows with RLS, or preserve history.

Rules:

- Use primary keys on every table.
- Use foreign keys for real ownership and relationship links.
- Index every foreign key column unless there is a specific reason not to.
- Prefer composite primary keys for pure join tables.
- Prefer constrained text values or Postgres enums for small state machines.
- Use partial unique indexes for rules like "one active couple per user".
- Keep user-facing and admin-only data separate when possible.
- Avoid loose polymorphic references when a real foreign key can model the relationship.
- Use `jsonb` only for bounded value objects that are normally read/written as a whole and do not need relational querying.
- Do not use one column per locale for localized content.
- Do not store secrets in tables directly exposed to client roles.

Common migration columns:

- Tables that are directly pulled by the local-first client must expose a stable UUID tie key, server-managed `created_at`, server-managed `updated_at`, and indexes matching their pull scope.
- Mutable directly synced rows must include `revision integer not null default 1`; the server increments it on each authoritative update.
- Soft-deletable directly synced rows must include `deleted_at` or be represented by a durable tombstone/read-model event.
- Append-only rows do not need update conflicts, but still need a stable cursor shape if they are directly pulled.
- Pure join tables may keep composite primary keys only when they are not directly synced. If a join table later becomes directly synced, add a surrogate `id` or expose it through a versioned read model with a stable UUID tie key.
- Every table with client-visible lifecycle state should use constrained text values or Postgres enums in the first migration, not free-form strings.

Good `jsonb` use:

- small widget metadata such as drawing bounds
- small future widget operation payloads if needed
- small device/client metadata
- StoreKit webhook payload archive in `internal`

Bad `jsonb` use:

- canonical widget drawing payloads
- large stroke/point arrays
- answer records
- relationship membership
- localized question text
- media ownership
- entitlement state

## Offline Mutation Envelope

Paeonia is offline-first. Server writes must be retry-safe.

Every user-initiated RPC that can be queued locally should accept a client operation envelope.

Recommended envelope fields:

```text
client_operation
- client_operation_id
- client_id
- client_sequence
- local_created_at
- idempotency_scope
```

Recommended internal table:

```text
internal.client_operations
- user_id
- client_operation_id
- client_id
- client_sequence
- operation_kind
- idempotency_scope
- request_hash
- response
- status
- created_at
- completed_at
```

Rules:

- `client_operation_id` is generated locally and stable across retries.
- `client_id` identifies the app install/device.
- `client_sequence` is monotonic per `client_id`.
- Use a unique constraint on `(user_id, client_operation_id)`.
- RPCs should return the original stored response when the same operation is retried.
- If the same `client_operation_id` is reused with a different request hash, reject it.
- Do not queue raw direct inserts for sensitive multi-table writes.
- Queue intent, for example `shuffle slot 2`, `submit answer`, or `save widget revision`.
- Storage uploads need a two-phase state: local draft, uploaded object pending server finalize, finalized metadata.
- Server rejection responses must be explicit enough for the app to roll back or refresh local state.
- Use last-write-wins only for low-risk settings. Use append-only records, immutable revisions, or server merge rules for product content.

RPCs that should use this envelope:

- invite creation and acceptance
- leaving/reporting
- daily challenge start/shuffle/answer
- thread creation and message send
- memory creation/update
- media finalize/delete
- widget drawing revision save
- latest location update
- report submission

## Remote Sync Contract

Paeonia should copy Tidex's mature sync direction from `ios/TidexApp/Storage/Sync/SyncCoordinator.swift`, `LocalSyncState`, and local SwiftData models.

Core lessons to copy:

- Local reads come from SwiftData repositories, not live network responses.
- User-facing writes update local state first and trigger sync.
- Pull sync uses server-managed `updated_at` cursors with an `id` tie-breaker.
- Do not use row revision alone as the pull cursor. Tidex kept revision for conflict checks but moved pull cursors to `updated_at` plus tie-breaker because new rows start at revision 1.
- Store sync state per signed-in user and, where needed, per active couple/sync stream.
- Persist the cursor only after a full page has been applied and saved locally.
- Save large pull pages in batches for durability, but advance the cursor only after the page succeeds.
- Pull before push so local conflict checks see the latest server state.
- Coalesce follow-up syncs when local changes happen during an active sync.
- Use bounded sync timeouts so a stuck sync cannot hold the sync lock indefinitely.
- Reset sync state on user change and purge local relationship caches when access is lost.
- Keep user-facing sync copy human, for example "Saved on this phone" and "Sending", not internal terms.

Recommended local model metadata for mutable synced records:

```text
local model sync metadata
- server_updated_at
- server_revision
- server_deleted_at
- sync_status
- dirty_fields
- last_synced_snapshot
- local_updated_at
- conflict_server_snapshot
```

Rules:

- `sync_status` values should start with `clean`, `dirty`, `pending_delete`, and `conflict`.
- `dirty_fields` should be typed per model where field-level merge matters.
- `last_synced_snapshot` stores the server baseline used for conflict detection.
- `conflict_server_snapshot` stores the server version when automatic merge is not safe.
- New locally-created records should use stable client-generated UUIDs where the server can accept them safely.
- Sensitive multi-table actions should not be represented as direct local table inserts. Queue intent through the offline mutation envelope and let RPCs own server-side transitions.
- Append-only and immutable content, such as answers, messages, widget revisions, and activity events, should avoid in-place local merge complexity.
- Low-risk user settings may use last-write-wins if the product impact is small and test coverage is explicit.

Recommended local sync state:

```text
local_sync_states
- owner_user_id
- scope_kind
- scope_id
- stream_key
- last_updated_at
- last_tie_id
- last_successful_sync_at
- last_sync_attempt_at
- last_sync_error
```

Rules:

- `scope_kind` examples: `user`, `couple`, `thread`, `widget_canvas`.
- `scope_id` is nullable only for pure user-level streams.
- `stream_key` examples: `profile`, `relationship`, `daily`, `memories`, `threads`, `media`, `widget`, `location`, `settings`.
- Cursor queries order by `(updated_at, stable_uuid_tie_key)` ascending.
- Pull queries use:
  - initial sync: first page ordered by `(updated_at, stable_uuid_tie_key)`
  - incremental sync: rows where `updated_at > last_updated_at` or `updated_at = last_updated_at and stable_uuid_tie_key > last_tie_id`
- `stable_uuid_tie_key` is normally the row's `id`. If the source table intentionally uses a different UUID primary key, the read model must expose it as the tie key.
- Every directly synced server row should have a stable UUID tie key, server-managed `created_at`, server-managed `updated_at`, and, for mutable rows, `revision`.
- Soft-deletable rows should expose `deleted_at` or an explicit tombstone payload until all active clients have had a chance to observe the delete.

Server read-sync shape:

- Use direct table pulls only for simple self-owned tables where RLS and row shape are straightforward.
- Use RPC/read-model sync for relationship-owned or sensitive surfaces:
  - current relationship state
  - entitlement-gated couple content
  - daily answer reveal state
  - thread/message inbox summaries
  - memory timeline summaries
  - widget current revision
  - partner location visibility
  - report status
- RPC sync responses should be typed and versioned, not loose unbounded JSON.
- Include enough tombstone information for the client to hide or purge local rows when access changes.
- Do not expose hidden relationship content after relationship end just to let clients delete it locally. Return minimal tombstone/read-model signals instead.

First-migration sync classification:

```text
direct table pull or simple self-owned view:
- own profile/settings
- notification_preferences
- user_devices
- privacy request status RPC/view

RPC/read-model sync:
- current relationship and pairing state
- entitlement state
- relationship access-loss events
- daily challenge, reveal, and answer state
- memory timeline, notes, and media metadata
- thread summaries and message pages
- widget current revision and revision history
- partner location visibility
- report status

internal/service only:
- invite secrets and invite attempts
- raw StoreKit payloads and transactions
- review access codes, attempts, and sessions
- notification outbox
- client operation idempotency rows
- cleanup job state
- report snapshots
- moderation actions
- privacy request audit events
```

Rules:

- Relationship-owned tables can still have normal relational constraints and indexes, but the app should sync them through typed read models unless a later migration intentionally exposes direct pulls for one surface.
- Composite-key tables such as answer-media joins, daily challenge ownership rows, and location preferences are read-model-only unless they gain a surrogate UUID tie key.
- Read-model responses must include `schema_version`, `updated_at`, and a stable UUID tie key for pagination when they are pageable.
- If a read-model payload aggregates multiple rows, include per-child IDs and moderation/deleted state so the client can update local caches deterministically.
- Direct self-owned streams may use the owner key as the stable tie key when it is already a UUID, for example `profiles.user_id` and `notification_preferences.user_id`.
- Mutable self-owned direct streams still need `updated_at` and `revision`, even when the tie key is not named `id`.
- Status-only self-owned streams such as privacy request status should be exposed through a narrow RPC/view if the raw table contains internal fields.

Required relationship access-loss surface:

```text
relationship_sync_events
- id
- user_id
- couple_id
- initiated_by_user_id
- event_kind
- reason
- occurred_at
- relationship_status
- member_status
- ended_at
- delete_after
- local_purge_scope
- created_at
- updated_at
```

Rules:

- `relationship_sync_events` is self-readable only by `user_id`.
- Relationship lifecycle RPCs insert an event for each affected member.
- Relationship leave/block audit is folded into `relationship_sync_events`; do not create a separate leave-event table for MVP.
- `initiated_by_user_id` is set when a user action caused the event and is null only for system/entitlement events.
- Event kinds start with `relationship_started`, `relationship_ended`, `entitlement_lost`, `entitlement_restored`, `content_cleanup_scheduled`, and `content_purged`.
- `local_purge_scope` is a constrained value or small bounded JSON object that tells the client which local namespaces to hide or purge, for example relationship content, location, widget cache, pending uploads, or entitlement cache.
- Access-loss events must not include hidden relationship content.
- The current relationship summary RPC returns the latest event cursor and minimal ended-notice state even after ordinary content is hidden.
- The client hides cached couple content immediately after applying a `relationship_ended`, `entitlement_lost`, or `content_purged` event.

Suggested first sync streams:

```text
user profile/settings:
- profiles
- notification_preferences
- user_devices
- user_entitlements via RPC cache only

relationship:
- current relationship summary RPC
- couple_members minimal state
- ended-notice state
- block state relevant to the current user

daily:
- today challenge read model
- daily answer reveal read model
- answer tombstones/moderation states

memories/media:
- memory timeline read model
- memory notes/media metadata
- pending upload/finalize states

threads:
- thread summary read model
- thread message pages per thread
- message/media tombstones

widget:
- active canvas and active revision
- revision history pages
- local App Group preview metadata

location:
- sharing preferences
- latest visible partner location only when both partners share
```

Deletion and purge rules:

- Local caches for an ended relationship must be hidden immediately after the relationship-end sync signal.
- The local store may retain encrypted-at-rest app cache files only as implementation cache, but UI must not expose closed relationship content.
- Server cleanup owns hard deletion after `delete_after`.
- Cleanup jobs must delete Storage objects through the Storage API or a verified server-side storage path, not by deleting only Postgres metadata.
- Report snapshots are excluded from relationship cleanup and follow report retention.

Tests required before feature work depends on sync:

- cursor pagination with identical `updated_at` values and different IDs
- local dirty row receives unchanged server row
- local dirty row receives conflicting server row
- pending delete survives app relaunch and retries
- relationship end hides local couple content
- re-pair does not restore old couple content implicitly
- failed page does not advance cursor
- queued local change during sync triggers follow-up sync

## Tidex Lessons To Copy

Paeonia should copy the durable parts of Tidex, not the product-specific parts.

Copy:

- Create an app-owned profile row when a Supabase Auth user is created.
- Use OAuth-provided name/avatar data as a fallback, not as the only source of truth.
- Treat Apple name data as best-effort because Apple may only provide it on first sign-in.
- Read sensitive entitlement state through server-side RPCs that use `auth.uid()`.
- Keep entitlement logic centralized on the backend.
- Use DB-backed reports for user-generated content.
- Have an explicit account deletion cleanup function before deleting the auth user.
- Use canonical pair modeling for one-to-one relationships, similar to Tidex's normalized direct-thread pair concept.
- Use `updated_at` plus ID tie-breaker cursors for pull sync.
- Keep server revisions on mutable local records for conflict checks.
- Use snapshot/event-style read models for message-like or relationship-owned content where direct table sync is too leaky.

Do not copy:

- Public usernames.
- User search.
- Public profile visibility.
- Public profile-photo buckets.
- Tidex's directional calendar-sharing relationship model.

Paeonia users are not discoverable. They only become visible to another user after an invite is accepted.

## Identity And Auth

### Auth Methods

MVP auth methods are:

- Sign in with Apple
- Google Sign-In
- passkeys

No email/password and no email magic-link auth in MVP.

Sign in with Apple private relay emails are valid normal accounts.

Rules:

- Do not require a real/non-relay email address for onboarding.
- Treat Apple-provided name and email as best-effort profile seed data.
- If Apple does not provide a name, ask for a display name in onboarding.
- Do not make App Review or TestFlight depend on a stable Apple relay email address.
- Account identity is the Supabase auth user id, not the email address.

### Account Creation Order

Onboarding order:

1. User starts onboarding.
2. User creates/signs into an account with Apple or Google.
3. User completes required profile setup, including display name fallback if needed.
4. User reaches a limited authenticated pre-entitlement state.
5. The limited state offers:
   - subscribe
   - restore purchases
   - accept invite
   - sign out
   - delete account
6. If the user subscribes or restores, entitlement attaches to the account.
7. If the user accepts an invite from an entitled partner, the couple becomes entitled through that partner.
8. After the account has direct entitlement or couple entitlement, the user can access the full product.

Reason:

- Entitlement is stored against a real account.
- Relationship content should not become usable without entitlement coverage.
- The non-paying partner still needs a way to accept an invite before they have direct entitlement.
- TestFlight users and App Review can create normal accounts with Sign in with Apple private relay and still complete review onboarding.
- This keeps the hard paywall while avoiding a dead end for the invited partner.

Limited pre-entitlement state:

- The user is authenticated but does not have full product access.
- The user may create a pairing invite only after direct entitlement is active.
- The user may accept a pairing invite before direct entitlement is active.
- Accepting an invite can create an active couple even when the accepting user is unentitled.
- Full product access unlocks only if the resulting couple has effective entitlement coverage through either partner.
- If the resulting couple has no effective entitlement coverage, both partners remain paywalled with a leave-relationship action.
- The limited state must make sign out obvious so users can recover from accidentally creating the wrong Apple/Google account.

### Passkeys

Passkeys are a sign-in method, not a sign-up method.

A user must already have an account before adding a passkey. The app can offer passkey setup after initial Apple or Google sign-in.

### Identity Linking

Supabase Auth can automatically link OAuth identities when verified emails match.

If a user accidentally creates a separate account because Apple and Google expose different emails, the post-auth onboarding flow must make it easy to sign out and try another provider before the user pays or pairs.

### Profile

Each auth user has one Paeonia profile.

Recommended fields:

```text
profiles
- user_id
- display_name
- profile_photo_asset_id
- time_zone_id
- time_zone_updated_at
- onboarding_completed_at
- revision
- moderation_status
- moderated_at
- moderated_by
- moderation_report_id
- created_at
- updated_at
- deleted_at
```

Rules:

- `display_name` is user-facing but not legal identity.
- `display_name` can be a nickname.
- `display_name` must be easy to change.
- OAuth name is used as a suggested/default value when available.
- If OAuth does not provide a usable name, onboarding asks the user for one.
- Profile photos are included in MVP because they create connection.
- Profile photos are visible only to the user and their current partner.
- Profile photos should use private storage, not public buckets.
- Profile display names and profile photos are reportable UGC.
- Profile moderation can hide the partner-visible display name/photo while keeping the account usable.
- `time_zone_id` stores the user's current IANA timezone, for example `Europe/Oslo`.
- Timezone should update when the app detects that the user has moved to another timezone.

## Relationship Model

Paeonia has one active couple per user in MVP.

The relationship is not a directed share. It is a shared private space between exactly two users.

Recommended core tables:

```text
relationship_pairs
- id
- user_low_id
- user_high_id
- created_at

couples
- id
- pair_id
- status
- started_on
- created_by_user_id
- created_at
- ended_at
- delete_after

couple_members
- couple_id
- user_id
- role
- status
- joined_at
- left_at
- ended_notice_seen_at

pairing_invites
- id
- created_by_user_id
- status
- expires_at
- accepted_by_user_id
- accepted_at
- revoked_at
- couple_id
- created_at

relationship_blocks
- id
- pair_id
- blocked_by_user_id
- blocked_user_id
- source_report_id
- created_at
- revoked_at
- revoked_by_user_id
- revoke_reason
```

`pairing_invites.couple_id` is nullable until the invite is accepted. The acceptance RPC creates the `relationship_pairs` row if needed, creates the `couples` row, creates both `couple_members` rows, and then stores the created `couple_id` on the invite.

Invite secrets should not live directly in the public invite metadata row. Keep invite code hashes/secrets in an internal table, for example:

```text
internal.pairing_invite_secrets
- invite_id
- code_hash
- created_at

internal.pairing_invite_attempts
- id
- code_hash_prefix
- matched_invite_id
- user_id
- success
- failure_reason
- ip_hash
- device_hash
- app_version
- attempted_at
```

Invite code rules:

- Invite codes are long random strings, not human words.
- Store only hashed invite codes using a server-side pepper or equivalent secret.
- Rate-limit invite preview and acceptance attempts before revealing inviter profile metadata.
- Attempt rows store coarse hashed IP/device identifiers for throttling and abuse review, not raw IP addresses when avoidable.
- The invite preview RPC returns only minimal inviter identity needed for the explicit accept screen.
- Failed lookup responses should not let an attacker distinguish "expired", "revoked", "accepted", and "never existed" codes until rate limits and authentication checks pass.

### Couple Status

Use simple backend states:

- `active`
- `ended`
- `deleted`

Avoid over-modeling the couple itself. More specific user-facing state belongs on `couple_members`.

### Relationship Invariants

Enforce these in the database, not only in Swift:

- A user cannot be paired with themselves.
- `relationship_pairs.user_low_id` is always less than `relationship_pairs.user_high_id`.
- `relationship_pairs` is unique on `(user_low_id, user_high_id)`.
- A `couples` row has exactly one `pair_id`.
- A couple can have exactly two members.
- A user can have at most one active couple membership.
- Use a partial unique index for active memberships, for example one active `couple_members` row per `user_id`.
- Use foreign keys for all content rows that belong to a couple.
- Index all foreign keys used by RLS helper functions and common relationship lookups.
- A relationship block must refer to a canonical `relationship_pairs` row.
- `blocked_by_user_id` and `blocked_user_id` must be different users and must match the two users represented by `pair_id`.
- Use a partial unique index so there is at most one active block per `(pair_id, blocked_by_user_id, blocked_user_id)` where `revoked_at is null`.
- `relationship_blocks` rows are created only by block/report/leave RPCs.
- A block can be revoked only by the blocking user through the unblock RPC or by a trusted service-role moderation runbook.
- Pairing invite creation and acceptance must reject active blocks in either direction.
- Ordinary clients should learn block state only through current relationship/pairing RPCs, not broad direct block-table reads.

### Member Status

Recommended member states:

- `active`
- `left`
- `ended_notice_pending`
- `ended_notice_seen`

Meaning:

- `active`: member currently has access to the relationship space.
- `left`: member initiated leaving or is no longer a participant.
- `ended_notice_pending`: member did not initiate the end and must see a one-time explanation.
- `ended_notice_seen`: member saw the explanation and can move on to the unpaired state.

### Pairing Flow

The MVP pairing flow is invite-only.

Rules:

- No user search.
- No public profiles.
- No way to check whether a person has an account.
- Pairing requires an invite shared outside the app.
- Accepting an invite requires the recipient to be authenticated.
- Pending invites do not create a couple row.
- The invite creator stays in a waiting-to-be-linked onboarding state until the recipient accepts.
- The waiting state should include a refresh action that checks whether the invite has been accepted and a couple now exists.
- Before acceptance, there are no active `couple_members` rows for that invite.
- On acceptance, create the couple even if neither partner currently has entitlement coverage.
- If the new couple has no effective entitlement, both partners see the paywall and an option to leave the relationship.
- One active couple per user.
- Invite codes should be stored hashed, not as plaintext.
- Expired/revoked/accepted invites cannot be reused.
- A user cannot accept their own invite.
- Entering an invite code must not immediately create the relationship.
- After a valid invite code is entered, show who is inviting the user and require an explicit accept action.
- If either user has an active block against the other user, invite creation and acceptance must be rejected.
- If there is a prior report/safety warning for the pair, show that warning before the accept action.
- Pairing always requires an active decision from both people: one creates the invite, the other reviews and accepts it.

### Canonical Pair Identity

Do not derive `couples.id` directly from user IDs.

Use `relationship_pairs` as the canonical identity for the two users:

- `user_low_id` and `user_high_id` store the two user IDs in deterministic order.
- `relationship_pairs` is unique on `(user_low_id, user_high_id)`.
- Each actual relationship session is still represented by a `couples` row.
- `couples.pair_id` points to the canonical pair.

Reason:

- It keeps relationship history explicit.
- It avoids reusing the same `couples.id` for multiple relationship sessions.
- It gives RLS and cleanup jobs a stable way to recognize the same two people if they re-pair.

MVP does not automatically restore old relationship content when the same two users re-pair.

Restoration rule:

- Ending a relationship hides old couple-owned content immediately.
- Hidden old content keeps its original `delete_after`.
- Re-pairing the same two users creates a new active `couples` row but does not clear, extend, or pause the old couple's `delete_after`.
- The cleanup cron owns deletion after `delete_after`.
- RLS should not expose old hidden content to a re-paired couple in MVP.
- If a graceful restore feature is added later, it must be an explicit backend RPC/product flow, not an implicit RLS side effect.

### Relationship End Flow

When either partner leaves:

1. The couple becomes `ended`.
2. The initiating member becomes `left`.
3. The other member becomes `ended_notice_pending`.
4. Both users immediately lose access to couple-owned content.
5. Local couple content disappears after sync.
6. Server keeps hidden content until `delete_after`.
7. A cleanup job deletes content and storage objects after roughly 30 days.

Important rule:

Do not silently return the non-initiating partner to the unpaired state. Show a one-time explanation.

Recommended copy:

```text
Your relationship space was closed.
You can no longer see the shared memories, drawings, or check-ins from this relationship.
```

Primary action:

```text
Continue
```

After the user taps Continue:

- set `ended_notice_seen_at`
- set member status to `ended_notice_seen`
- move the app to the unpaired state

Use calm product wording. Do not say "your partner left you" in the main UI.

### Content Visibility After Relationship End

Relationship-owned content is hidden immediately when the relationship ends.

This includes:

- memories
- memory photos
- memory notes
- voice notes
- prompt answers
- streak state
- countdowns
- widget drawings
- widget drawing rasters/cache

Hidden means:

- RLS denies ordinary user access.
- Sync removes local visibility.
- The rows may remain server-side until the deletion window ends.

Exception:

- Minimal relationship metadata must remain readable long enough to show the one-time ended notice.
- This metadata should not include relationship content.
- Allowed fields should be limited to what the client needs, for example relationship status, `ended_at`, `delete_after`, and the current member's notice state.

## Account Deletion

Deleting an account while in an active couple should first run the same relationship transition as leaving.

Rules:

- If the deleting user is in an active couple, the couple becomes `ended`.
- The deleting user is treated as the initiating member.
- The remaining partner gets the same one-time ended notice as an ordinary leave.
- Couple-owned content is hidden immediately and deleted after the normal deletion window.
- The deleting user's profile is anonymized immediately: clear display name, profile photo, location sharing, devices, notification preferences, and user-editable profile fields that are not needed for audit or legal/security retention.
- Account deletion must clean up or disable devices, notification preferences, location sharing, and active sessions.
- Account deletion should not bypass the relationship leave audit row.
- If the deleting user has an active subscription, the app should direct them to Apple's subscription management flow before or during deletion.
- If the user signed in with Apple, account deletion must include Sign in with Apple token revocation handling.
- Do not assume Supabase fully handles Sign in with Apple token revocation until verified during auth implementation.
- If Supabase Auth does not expose enough provider-token data for deletion-time revocation, Paeonia needs a secure server-side Apple token capture/revocation path or a re-auth-on-delete flow.
- Account deletion cannot ship until Sign in with Apple revocation behavior is verified end to end.
- Server-side cleanup must happen before deleting the Supabase Auth user, or through a trusted cleanup function that can still identify the deleted user.
- Do not use `ON DELETE CASCADE` from `auth.users` to couple-owned content, reports, leave events, StoreKit audit rows, or privacy request audit rows.
- Long-lived audit tables that must survive auth-user deletion should store UUID snapshots and avoid hard dependencies on a live profile row.
- Short-lived self-owned tables such as devices, notification preferences, location sharing preferences, and unfrozen pending uploads can be deleted or disabled during `delete_account()`.
- The final auth-user deletion is the last step after relationship end, profile anonymization, session revocation/sign-out, Apple token revocation, and internal cleanup have succeeded or been queued in a retryable job.
- If an auth user cannot be hard-deleted immediately because StoreKit, report, or legal retention still needs stable identifiers, mark the profile deleted/anonymized and keep a restricted internal deletion job until hard deletion is safe.

Reason:

- The remaining partner should experience the same clear relationship end state.
- We avoid a second relationship termination model.
- Cleanup jobs can reuse the same hidden-then-delete path.

## Entitlement Direction

The entitlement should be tied to the user and bleed into the relationship they are currently in.

Working rule:

- Entitlement is user-owned.
- A couple is usable when at least one active member has an active entitlement.
- Only one partner needs to pay.
- Both partners get access while the current couple has entitlement coverage.
- Lifetime access can be granted to selected users.
- A paying unpaired user can invite a new partner without paying again.
- If the paying partner leaves, the relationship ends for both partners.
- If the non-paying partner leaves, the payer keeps the subscription and returns to the unpaired state.
- If the subscription expires, the relationship remains but both users lose access behind the paywall until entitlement is restored.
- If Apple reports the subscription in grace period, keep full access while grace remains active.
- If Apple refund/revocation happens, access stops immediately.
- Before launching StoreKit, the client should ask the backend whether the current relationship already has effective entitlement coverage.
- If the relationship is already covered, do not start the subscription purchase flow.
- The backend cannot prevent a valid Apple transaction after StoreKit has already completed.
- If two purchase flows somehow complete, record both valid transactions, but do not create duplicate relationship access. The couple is simply covered by at least one active entitlement.
- If a relationship is active but not entitled, both partners can see the paywall and a leave-relationship action.

### App Review Access

Paeonia should be a free App Store download with a hard StoreKit in-app purchase paywall.

Reason:

- A paid download would make both partners pay just to install.
- A free download with IAP lets one partner pay while the other partner signs in and receives access through the couple entitlement.
- Apple can test the purchase flow in sandbox without a real charge.

App Review setup:

- Provide App Review with at least one pre-paired, entitled review code that can immediately show the full app after the reviewer signs in with Apple or Google.
- Provide one unpaired, unentitled review code for sandbox purchase testing after normal sign-in.
- Provide a short screen recording of onboarding and invite pairing.
- Do not make App Review success depend on live invite-flow testing, two app instances, or manually switching between two fresh accounts; provide the onboarding/pairing screen recording instead.
- Keep the seeded demo partner account non-expiring.
- Because normal auth is OAuth/passkey-only, provide a review-only access code flow after normal Apple/Google sign-in instead of shared credentials.
- Explain in App Review Notes that one subscription covers one private couple.
- Explain that review access is a review-only grant and is not a user-facing payment bypass.
- Do not rely on Apple Family Sharing for the partner entitlement model.
- Support sandbox StoreKit transactions and sandbox App Store Server Notifications before submission.

Review-only auth path:

- Add a hidden/documented App Review entry point, for example a "Review Access" action on the sign-in screen that is mentioned only in App Review Notes.
- App Review signs in with the normal Apple or Google auth flow.
- After normal sign-in, the reviewer enters a revocable review code from App Review Notes.
- The app calls an authenticated trusted backend flow, for example `redeem-review-access`.
- The backend validates the review code against `internal.review_access_codes`.
- The backend applies the requested review scenario to the currently authenticated `auth.uid()`.
- A pre-paired paid review scenario grants the signed-in review user a review entitlement and pairs them with a seeded demo partner account.
- A purchase-flow scenario can leave the signed-in review user unpaired and unentitled so Apple can test sandbox StoreKit.
- The review flow must not create normal user-facing payment bypasses.
- The review flow must not use email/password, email OTP, email magic links, or shared seeded account credentials.
- The backend creates an auditable `internal.review_access_sessions` row for each redemption.
- The backend applies `internal.entitlement_grants.grant_kind = review` to the signed-in reviewer account when the scenario requires paid access.
- Review codes must be disabled outside review windows when not needed.
- Review access must not appear as a normal user-facing payment bypass.
- Normal users still get only Apple, Google, and passkey sign-in.
- Email magic-link auth is not used for review access and is not exposed as a normal sign-in method.
- The review access Edge Function should require a user JWT because the reviewer signs in normally before redeeming the code.
- The review access Edge Function must implement rate limiting or attempt throttling before validating codes.
- Store only hashed review codes, using a server-side pepper from Edge Function secrets.
- Review codes should be long random strings, not human words.
- Review codes can be scoped only to one of the two MVP review scenarios: `pre_paired_entitled` or `purchase_flow_unentitled`.

Review access sequence:

1. Reviewer signs in with Apple or Google.
2. App shows the review-only code screen from the documented App Review entry point.
3. Reviewer enters the review code.
4. App calls the authenticated review-access backend with code, app version, and coarse device metadata.
5. Edge Function hashes the code with the server pepper and records an `internal.review_access_attempts` row for `auth.uid()`.
6. Edge Function rejects inactive, expired, revoked, over-redeemed, or rate-limited codes.
7. Edge Function creates `internal.review_access_sessions` for `auth.uid()`.
8. Backend applies the selected scenario to `auth.uid()`.
9. For pre-paired review, backend grants review entitlement and creates or restores a review-only couple with the seeded demo partner account.
10. For purchase-flow review, backend records the session but does not grant entitlement.
11. App calls authenticated RPC `complete_review_access_session(review_session_id)` if the Edge Function did not complete it in the same transaction.
12. Backend checks `auth.uid()` matches `internal.review_access_sessions.user_id` before marking the session complete.
13. App continues through the same post-auth routing used by Apple, Google, and passkey sign-in.

Review access migration rules:

- `internal.review_access_sessions.couple_id` links any review-created couple back to the redemption.
- `internal.review_access_sessions.entitlement_grant_id` links any review-created grant back to the redemption.
- If the signed-in reviewer is already in an active non-review couple, pre-paired review redemption must fail with a clear "leave current relationship first" response instead of silently ending or replacing that relationship.
- If the signed-in reviewer already has an active review couple from the same scenario, redemption may return that existing couple instead of creating another.
- Review-created couples should be marked in internal audit metadata, not by exposing a normal user-facing "review couple" status.
- Revoking a review session should revoke its linked review entitlement grant and end/hide the linked review couple if it exists.
- Review grants default to expiring at the end of the App Review window unless a deliberate longer expiry is set for TestFlight or beta review.
- Review access throttling should include user id, code hash prefix, IP hash, and device hash so a signed-in reviewer account cannot brute force codes across devices.

## Widget Drawing Direction

The widget is a canvas for partner expression.

Rules:

- Drawing content is first-class product content.
- Users do not draw directly inside the Home Screen widget.
- Tapping the widget opens the app to the drawing canvas.
- The user draws in the app, saves, and the widget updates from the latest saved revision.
- MVP drawing implementation uses PencilKit.
- Use `PKCanvasView` for the in-app drawing surface.
- PencilKit is not Apple Pencil-only. The canvas should allow finger input as well.
- Drawings are stored as vector/stroke data.
- Canonical vector drawings are stored as immutable `PKDrawing` payloads.
- Postgres stores revision metadata, validation fields, hashes, and pointers to Storage objects.
- Use `PKDrawing.dataRepresentation()` as the canonical saved payload.
- If Paeonia later needs a custom cross-platform renderer, add a new format version using a typed binary format such as Protobuf or CBOR instead of large JSON point arrays.
- Drawings are rasterized on device for widget rendering and local thumbnails.
- Use `PKDrawing.image(from:scale:)` for derived preview rendering.
- Raster output is derived/cache data, not the canonical source.
- Widget payloads must be privacy-aware because they can be visible outside the app.

Rules:

- `widget_canvases.couple_id` is unique.
- `payload_media_asset_id` references the finalized `media_assets` row for the canonical drawing payload.
- `format` should be `pkdrawing`.
- `format_version` starts at `1`.
- Do not overwrite drawing payload objects.
- Canonical drawing payload uploads use the shared `media_assets` pending/finalize/delete lifecycle.
- A drawing revision becomes visible only after the linked `media_assets` row is finalized and the save-revision RPC validates ownership, reserved path, byte limit, declared hash, and cheap metadata invariants.
- `media_assets.bucket` should be `widget-drawings` for canonical drawing payloads.
- `media_assets.media_type` should be `drawing_payload` for canonical drawing payloads.
- Do not store every stroke point as a database row in MVP.
- Do not store large whole-drawing point arrays as `jsonb` in MVP.
- Small JSON is acceptable for metadata such as bounds or future operation payloads.
- Do not add a server-side raster table or `widget-rasters` bucket for MVP.
- Derived raster previews are local App Group cache files generated from the canonical vector payload on device.
- Recommended canonical object path: `widget-drawings/{couple_id}/{canvas_id}/revisions/{revision_id}/drawing.pkdrawing`.
- Enforce reasonable `stroke_count` and `point_count` limits.
- MVP stroke limit: maximum 5,000 strokes per saved revision.
- MVP point limit: maximum 200,000 points per saved revision.
- MVP payload limit: 2 MB normal hard limit, with a 5 MB admin/debug escape hatch only if needed.
- If PencilKit does not expose reliable stroke/point counts for every future OS version, treat counts as best-effort metadata and enforce the hard byte limit as the primary guardrail.
- Single realtime/broadcast events should send notifications only, not full drawings.
- The iOS app must validate that the payload can be decoded into `PKDrawing` before upload/finalize.
- The Supabase backend cannot natively decode PencilKit payloads in Postgres/Deno, so server validation is limited to authorization, immutable path ownership, byte limits, declared metadata, hash checks, MIME/extension checks, and finalize state transitions.
- Treat client-side `PKDrawing` decode validation as a required precondition, but not as an authorization boundary.
- Store `client_decode_validated_at`, `client_renderer_version`, and `client_validation_version` on finalized revisions for audit/debugging.
- Validate cheap invariants in Postgres with `CHECK` constraints.
- Use `media_assets.sha256` so downloads can be verified and duplicate uploads can be detected.
- Only the latest active revision needs to be sent to the widget.
- Preserve complete drawing history.
- History should show who drew/edited and when.
- Continuing a drawing creates a new revision with the full current drawing payload.
- Clearing the canvas is local editing state until the user saves.
- Only saving inserts a new `widget_drawing_revisions` row.
- If the user clears the canvas and then saves, the saved revision contains the new full payload.
- Either partner can clear the canvas.
- Stroke colors are stored in the payload.
- Keep vector history indefinitely unless the relationship content is deleted.
- Older history thumbnails can be rasterized from vector data on device, off the main thread.
- Rasterization should happen on device, not in the database.
- Widget is Home Screen only for MVP, not Lock Screen.
- No Lock Screen redaction behavior is needed for MVP.
- The widget should read prepared local App Group preview files and metadata, not parse the full vector payload directly.
- When a partner saves a new revision, send the other partner a silent push to wake the app, sync the new revision metadata, render local preview files, update App Group metadata, and reload the widget timeline.
- Silent push is a best-effort refresh trigger, not the only source of truth. The app must also refresh when opened.

```json
    "systemLarge": "Widget/previews/systemLarge.png"
  }
}
```

Rules:

- App Group payload is local cache only.
- Canonical drawing state remains the private `.pkdrawing` Storage payload and `widget_drawing_revisions` metadata.
- Do not put raw `PKDrawing` data in the App Group widget payload.
- Do not include note text, answer text, voice data, precise location, invite codes, or report data.
- Use atomic writes: write preview/metadata to temporary files, then replace.
- If metadata is missing, invalid, stale, or references missing preview files, the widget should show a safe placeholder.
- If `privacyMode = redacted` or `isRedacted = true`, show a neutral placeholder instead of the drawing.
- `contentHash` should change when the rendered preview content changes so the widget can avoid stale display.
- The app refreshes this payload after saving a drawing, after syncing a partner revision, and on app open.
- Silent push may trigger refresh, but the payload must remain correct if silent push is delayed or dropped.

Deletion and moderation propagation:

- If relationship access ends, entitlement is lost, or account deletion begins, the app must remove widget preview files and replace `Widget/current.json` with a redacted placeholder state on next sync/open.
- If the active revision is admin-hidden or removed, the app must not render that revision in the widget.
- If no visible current revision exists, show a neutral placeholder.
- Do not fall back to an older visible revision automatically for the main widget unless the product explicitly adds a history mode later.
- Local App Group files are cache and may be deleted at any time.
- Server cleanup of canonical drawing payloads follows the shared `media_assets` Storage cleanup rules.

Implementation checklist:

- Wrap `PKCanvasView` for SwiftUI.
- Load the active revision's `PKDrawing` payload into the canvas.

- On app open, sync latest widget revisions even if silent push was missed.

### Couple Days And Question Assignment

The database stores the question bank. The daily challenge is composed at runtime when the user starts the daily challenge in the app.

The app should not rely on a scheduled cron job to pre-generate all daily questions.

The app sends user intent. The backend owns the rules.

RPCs:

- `start_daily_challenge()` creates or returns today's three slots.
- `shuffle_daily_question(slot_number)` records the skipped question and returns a valid replacement while enforcing the daily challenge shuffle limit.
- `submit_daily_answer(instance_id, payload)` validates the allowed answer kinds, writes answer rows, and applies reveal/completion side effects.

Reason:

- The behavior can be fixed or tuned server-side without shipping a new iOS build.
- Old app versions keep calling the same RPCs and receive corrected rules.
- Offline-first retries can queue intent such as "shuffle slot 2" instead of replaying unsafe direct inserts.

Recommended flow:

1. User taps the daily challenge button.
2. The app calls a backend RPC for the current couple day.
3. The backend filters eligible questions.
4. The backend randomly selects candidates for open slots.
5. The backend creates the `couple_day`, `daily_challenges`, and `daily_question_instances` rows if needed.
6. The app displays the returned instances.

Reason:

- The question catalog stays server-controlled.
- The daily experience can feel immediate.
- Randomization rules stay consistent across devices and app versions.
- Modified clients cannot bypass shuffle, answered-question, inactive-question, or suppression rules.
- The app still owns the user experience, but not the authority to insert arbitrary daily questions.

Backend validation responsibilities:

- The caller is an active member of the couple.
- The couple has effective entitlement.
- The couple day is computed from stored partner timezones.
- The slot exists and is unanswered before shuffle.
- The user has used fewer than 5 shuffles for the current daily challenge across all three assigned slots.
- The question is active and has required localizations.
- Non-resurfaceable questions must not be selected again after the user has answered that question identity.
- Resurfaceable questions may be selected again when the user's latest answer to that question identity is older than the configured resurfacing window.
- The question is not currently suppressed by an active shuffle row.
- Only one active instance exists per `(couple_day_id, seeded_for_user_id, slot_number)`.
- Repeated requests are idempotent where possible.
- `start_daily_challenge()` and shuffle should run in transactions and lock the affected couple-day/user/slot state to avoid duplicate slot assignment under concurrent retries.

Each partner unlocks three random questions for the couple day anchored to the user in the earliest timezone.

The two partners do not have to receive the same three questions.

Each user's daily challenge is to answer three of their own assigned questions.

If a user dislikes an unanswered candidate question, they can shuffle it. Each user gets 5 total shuffles per daily challenge across all three of their assigned questions. The skipped question is recorded and excluded from that user's candidate pool for 14 days.

Shuffling rules:

- Shuffling is tracked per user, not on `profiles`.
- Use `daily_question_shuffles` or a similar normalized table.
- A user can shuffle unanswered slots up to 5 total times per daily challenge.
- The 5-shuffle limit spans all three assigned slots, not each slot separately.

When one partner answers one of their assigned questions, that question appears in the other partner's answered-questions screen. The other partner can answer it even if it was not part of their original three. If both partners received different questions, each partner can therefore answer up to six daily questions: their own three plus the partner's three.

Recommended tables:

```text

```

Rules:

- `couple_days` is unique on `(couple_id, local_date)`.
- `daily_challenges` has primary key `(couple_day_id, user_id)`.
- `daily_question_instances.status` is constrained, for example `active`, `shuffled`, `answered`.
- Only one active instance may exist per `(couple_day_id, seeded_for_user_id, slot_number)`.
- Use a partial unique index for active slots.
- `seeded_for_user_id` must be an active member of the couple.
- Each active member gets three instances per couple day.
- The same question may be selected for both partners on the same couple day.
- Reveal is per `daily_question_instance`, not per stable question identity.
- If the same question appears in both partners' seeded sets on the same day, each instance is still answered/revealed independently.
- A user's daily challenge is complete when the user has answered all three instances seeded for them, and `daily_challenges.completed_at` is set.
- A user can answer partner-seeded instances from the answered-questions screen.
- Answering partner-seeded instances does not replace the user's own three-question challenge.
- A shuffled question must not reappear for the same user until `exclude_until`.
- A user can have at most 5 shuffle rows for one `(couple_day_id, user_id)` daily challenge.
- `daily_question_shuffles` stores skipped questions and the time window where they are suppressed.
- `daily_question_shuffles.skipped_instance_id` points to the instance that was shuffled away.
- `daily_question_shuffles.replacement_instance_id` points to the replacement instance returned by the shuffle RPC.
- Do not show non-resurfaceable question identities that the same user has already answered.
- A resurfaceable question can appear again when the user's latest answer for that question is older than `questions.resurface_after_months`, defaulting to 6 months.
- When a resurfaceable question appears again, show the user's old answer history for that question with answer dates.
- The user can write a new answer on the new instance.
- If the old answer still applies, the user can shuffle the question instead.
- Starting the daily challenge freezes `anchor_time_zone_id`, `starts_at`, and `ends_at`.
- If a partner moves timezone during the day, the current `couple_day` does not change.
- The next started `couple_day` uses the latest stored partner timezones.
- When a partner completes their three-question challenge, notify the other partner.
- Notification copy should explain that answering the questions is required to reveal what the partner wrote.

Shuffle lifecycle:

1. `shuffle_daily_question(slot_number)` locks the active unanswered instance for that user/slot.
2. The old instance becomes `status = shuffled`.
3. The backend inserts a `daily_question_shuffles` row with `skipped_at` and `exclude_until = skipped_at + interval '14 days'`.
4. The backend chooses a valid replacement question.
5. The backend inserts a new `daily_question_instances` row for the same slot with `status = active`.
6. The old instance's `replaced_by_instance_id` points to the new instance.

Answered-question history:

- Answered history is stored by `daily_question_answers`.
- To find what a user has answered, join `daily_question_answers -> daily_question_instances -> question_versions -> questions`.
- Use this history to exclude non-resurfaceable question identities and to decide whether resurfaceable questions are old enough to show again.

Rules:

- `storage_path` is unique within `bucket`.
- `sha256` stores the content hash supplied during finalize.
- Use private buckets.
- Use signed URLs or authenticated downloads.
- Use separate private buckets:
  - `profile-photos`
  - `couple-media`
  - `widget-drawings`
  - `report-snapshots`
- Recommended object paths:
  - `profile-photos/{user_id}/{asset_id}.{ext}`
  - `couple-media/{couple_id}/{media_type}/{asset_id}.{ext}`
  - `widget-drawings/{couple_id}/{canvas_id}/revisions/{revision_id}/drawing.{format_ext}`
  - `report-snapshots/{report_id}/{asset_id}.{ext}`
- Use short-lived signed URLs by default. Start with 15 minutes unless implementation testing shows a need for a longer window.
- `owner_user_id` points to the uploader/creator.
- `couple_id` points to the relationship context when the asset belongs to relationship content.
- `reserved_parent_kind` is a constrained value that records the content surface the upload is reserved for, for example `profile_photo`, `memory_media`, `daily_answer_media`, `thread_message_media`, `widget_drawing_revision`, or `report_snapshot`.
- `reserved_parent_id` stores the UUID of the parent content row, using a stable client-generated UUID when the parent row will be created by the same queued operation.
- `reserved_by_client_operation_id` links the pending upload reservation to the queued local operation that requested it when the upload is part of an offline mutation.
- `upload_purpose` is a constrained value that records why the object is being uploaded, for example `profile_photo`, `memory_photo`, `voice_note`, `daily_answer_media`, `thread_media`, `widget_drawing_payload`, or `report_snapshot`.
- `expected_media_type` and `expected_bucket` store the finalize-time contract chosen by the reservation RPC. Finalize must reject mismatches instead of trusting client-supplied values.
- Profile photos may have `couple_id` null but are still not public.
- For profile photos, prefer the user-uploaded photo and fall back to the OAuth avatar when available.
- Voice notes are stored as media assets with `media_type = voice`.
- Canonical widget drawing payloads are stored as media assets with `media_type = drawing_payload`.
- Images should adapt Tidex's `ImageCompressor` pattern: prefer efficient formats when supported, keep JPEG fallback, resize/compress before upload, and store resulting metadata.
- Memory photos allow up to 5 photos per partner per memory.
- Voice notes can attach to daily answers, memories, and threads.
- Upload status starts with `pending`, `finalized`, `failed`, and `expired`.
- Only finalized, non-deleted, non-hidden media can be returned in ordinary read models or signed URL flows.
- MVP does not include external media scanner fields or a scanning vendor integration.
- MVP uses manual/service-role quarantine: content is normally visible after finalize, then reports or service-role review can mark content `pending_review`, `hidden`, `removed`, or `rejected`.
- `pending_review`, `hidden`, `removed`, and `rejected` media must not be exposed through ordinary signed URL flows.
- Profile photos, memory photos, daily answer media, thread media, voice notes, canonical widget drawing payloads, and uploaded report snapshots all use the same upload/finalize/delete retry model where practical.
- Relationship media is hard-deleted by the relationship cleanup job after the relationship deletion window.
- Storage cleanup must delete objects through the Supabase Storage API or an approved server-side storage path, not by only deleting database metadata.
- Cleanup jobs should delete Storage objects first or mark them for retry, then finalize `media_assets.deleted_at`/hard-delete metadata when object deletion succeeds.
- Relationship cleanup must cover `couple-media` and `widget-drawings`.
- Relationship cleanup must not delete `report-snapshots`; report snapshot retention is controlled by `internal.report_snapshots.delete_after` and `internal.report_snapshot_assets.delete_after`.

Upload/finalize model:

- Use pending DB metadata first.
- The app asks an RPC to create a pending upload row and reserve an immutable final Storage path.
- The app uploads directly to that final path.
- The app calls a finalize RPC with byte size, content type, checksum, and related metadata.
- The finalize RPC verifies the pending row, reserved object path, owner, couple, parent context, upload purpose, expected bucket, expected media type, client operation linkage, byte limits, checksum, and parent content before marking it usable.
- If upload succeeds but finalize fails, cleanup jobs can find and remove stale pending objects.
- Do not use temp-object move/rename as the MVP path.

Required pending/delete fields on `media_assets`:

```text
upload_status
upload_expires_at
upload_finalized_at
sha256 or content_hash
reserved_parent_kind
reserved_parent_id
reserved_by_client_operation_id
upload_purpose
expected_media_type
expected_bucket
storage_delete_status
storage_deleted_at
storage_delete_attempts
last_storage_delete_error
```

Rules:

- The first migration should include these fields on `media_assets`; upload-backed content tables should reference the finalized media row instead of duplicating lifecycle columns.
- Pending upload rows expire if finalize is not called before `upload_expires_at`.
- Cleanup jobs delete expired pending objects and mark failed deletes for retry.
- Finalize RPCs must be idempotent through `internal.client_operations` and reject attempts to finalize a path reserved for another user, couple, parent row, media type, or operation.

- Reports for couple-owned containers must still resolve to one partner; if the target cannot map to exactly one non-reporter user, reject the report and ask the client to use a more specific target.
- Admin-only review state and reviewer notes should live in `internal` if ordinary clients do not need to read them.
- Admin-only review/update paths should be server-side.
- Add a user-visible block/leave path in MVP.
- Reporting should offer a "block and report" path.
- Blocking can also be available as "block and leave" without a report.
- In MVP, blocking/reporting is the functional contact cutoff: after a relationship is closed, the blocked partner cannot message, view content, invite, re-pair, or interact through the app unless the blocking user explicitly unblocks later.
- Because Paeonia has no user search, public profiles, or unsolicited in-app invites, there is no general-purpose inbound contact surface to block.
- Labeling the safety cutoff as blocking reduces App Review risk for private user-generated content.
- A normal leave does not prevent re-pairing and does not show a safety warning.
- A block prevents re-pairing while active.
- A report creates a pair safety warning and may also create an active block if the reporter chooses block/report.
- If the same two users try to pair again after a previous report but no active block exists, show an abuse/safety warning before they continue.
- Re-pairing after a report still requires a new invite and an explicit accept action from the invited user.
- Re-pairing after a block requires the blocking user to unblock first.
- Pair safety warning flags are kept permanently unless we later define an explicit admin removal workflow.
- The safety warning should be surfaced by the accept-invite RPC response, not by exposing broad report history to the client.
- Admins can hide/remove specific reported content without deleting the whole relationship.
- Admins should only be able to view content that was reported or content needed to review that report.
- Snapshot reported content internally for review, even if the user later deletes or loses access to the original content.
- Store text/metadata snapshots in the internal report row and binary media snapshots in the private `report-snapshots` bucket when needed.
- Track binary report snapshot objects in `internal.report_snapshot_assets`.
- Binary report snapshots are queued in SQL and copied by a trusted service using the Supabase Storage API. The queue stores the source object, destination object, copy state, retry metadata, and later deletion state; ordinary clients never write or read `report-snapshots` directly.
- Keep report snapshots while the report is open.
- After a report is resolved, keep snapshots for 180 days, then delete snapshot rows and `report-snapshots` storage objects.
- Keep the report row, moderation actions, and pair safety warning flag after snapshot deletion.
- Relationship cleanup jobs must skip report snapshot rows and objects even when the original relationship content is deleted.
- The reported user is not notified that they were reported.
- `internal.moderation_actions.operator_kind` starts with `service_role`, `sql_runbook`, `edge_function`, and future `admin_user`.
- `operator_identifier` stores the runbook name, function name, deployment identity, or internal admin identifier responsible for the action.
- `reviewer_user_id` is nullable for MVP service-role/SQL runbook actions because no admin user table exists yet.
- `runbook_id` should point to a documented internal procedure or migration/runbook note when the action is performed manually.
- `action_kind` starts with `hide`, `remove`, `restore`, `reject_upload`, `delete_storage`, `create_pair_warning`, `clear_pair_warning`, `block_pair`, and `unblock_pair`.
- `status` starts with `started`, `applied`, `partially_applied`, and `failed`.
- Moderation runbooks must record previous/new moderation status and any Storage cleanup action so manual quarantine remains auditable.

## Content Ownership Matrix

Default model:

- Relationship content is couple-owned for visibility, lifecycle, entitlement, and cleanup.
- Individual contributions are user-authored for attribution, limits, reporting, and moderation.
- Ending a relationship hides couple-owned content immediately.
- The cleanup job deletes hidden couple-owned content after the deletion window.
- Re-pairing does not pause, clear, extend, or bypass the old content deletion window in MVP.
- Admin-hidden or admin-removed content must stay hidden even if the same pair later creates a new relationship.

Owner:

- `profiles.user_id`

- Partner access to the profile photo disappears when the relationship ends.

## RLS Direction

Do not write final RLS before schema exists.

But schema must be designed so RLS can express these rules cleanly:

- A user can read their own profile.
- A current partner can read the other partner's profile fields needed by the app.
- No one can list/search users.
- Couple-owned content is readable only while the user is an active member of an active, entitled couple.
- Ended relationship content is hidden from both members until deletion.
- `internal.can_access_couple_content(content_couple_id)` must require active membership in that same active couple for MVP.
- It must not grant access through old `relationship_pairs` membership or a newly re-paired couple.
- Entitlement checks are enforced server-side.
- Reports are visible to the reporter and admins, not the reported user.
- Admin access should use explicit admin checks, not broad client policies.
- Complex reveal rules and relationship access checks may need security-definer helper functions for performance and correctness.
- RLS helper functions should use indexed lookups and wrap `auth.uid()` as `(select auth.uid())` in policies where applicable.
- Daily question screens should use RPCs or views shaped for the UI instead of broad direct table reads.
- The today screen may reveal that a partner answered and when they answered.
- Answer content rows must remain hidden until the current user has answered the same instance.
- Since users cannot delete answers and MVP avoids in-place answer editing, answer detail rows can be treated as historical after insert except for admin moderation fields.
- Report review access should be admin/RPC-controlled and limited to reported content.

### RPC Security Pattern

Default pattern:

- Client-callable database RPCs live in an exposed schema only as narrow wrappers.
- Exposed wrappers should be `security invoker` unless there is a reviewed reason otherwise.
- Privileged logic and reusable authorization helpers live in `internal` or another non-exposed schema.
- Security-definer functions must not live in exposed schemas.
- Security-definer functions must set a fixed `search_path` and fully qualify table references.
- Revoke broad execute privileges first, then grant execute only to the required roles.
- Use `(select auth.uid())` or a local variable derived from it for user identity checks.
- Do not use `raw_user_meta_data`, `user_metadata`, display name, email address, or provider metadata for authorization.
- Flows that need service-role access, secret peppers, StoreKit signing validation, Storage cleanup, or internal snapshots should run through Edge Functions with JWT verification when user-initiated.
- Edge Functions that are user-initiated must verify the user JWT and pass the authenticated user id into trusted internal functions.
- Webhooks, cron jobs, and cleanup functions may use service role and should be idempotent.
- Every user-queued write RPC that can be retried should use `internal.client_operations`.

First-migration grants:

- `anon` gets no direct table access.
- `authenticated` gets direct table access only where the actor matrix says self-owned direct access is acceptable.
- `authenticated` gets execute only on the public RPC wrappers needed by the app.
- `authenticated` may get execute on specific internal security-definer functions only when those functions are not in an exposed schema and cannot be called directly through the Data API.
- `service_role` owns internal operations, cleanup, report snapshots, review-code setup, StoreKit reconciliation, and moderation runbooks.

- `couple-media`

- `widget-drawings` uploads require matching pending `media_assets` ownership/context and a save-revision finalize RPC
- `report-snapshots` writes are internal/admin-only
- downloads use signed URLs or authenticated access
- report snapshots are internal/admin-only

### RLS Actor Matrix

Default stance:

- `anon` has no direct table access.
- `authenticated` direct writes are allowed only for simple self-owned settings.
- Sensitive writes are RPC-only.
- Internal schemas are not exposed to ordinary clients.
- Service role and trusted Edge Functions may bypass user RLS only for internal jobs, webhooks, cron, admin review, and cleanup.

Policy actors:

- `self`: `auth.uid()` owns the user row.
- `active_member`: user is an active member of the row's active couple.
- `entitled_member`: active member and the couple has effective entitlement.
- `reporter`: user created the report.
- `admin`: internal admin check, never user-editable metadata.
- `service`: service role / trusted backend job.

Use helper functions for actor checks:

- `internal.current_user_id()`
- `internal.is_active_couple_member(couple_id)`

- Put security-definer helpers in `internal` or another non-exposed schema.
- Set fixed `search_path`.
- Fully qualify table names.
- Grant execute narrowly.
- Back helper predicates with indexes.
- Do not use user-editable metadata for authorization.

Views/read models:

- Use views with `security_invoker = true` where direct views are exposed.
- Prefer RPC/read models for daily question reveal state.
- Read models may expose partner answered/answered_at metadata without answer body.
- Answer body/media reads must go through `can_view_daily_answer`.
- Relationship/access read models must expose ended/access-lost/tombstone events without exposing hidden content.
- Location read models must distinguish not-sharing, disabled, stale, and relationship-ended states.
- Memory, thread, widget, and media read models must include moderation/deleted states so local caches can remove hidden content deterministically.
- Admin review read models should be internal/RPC-controlled and scoped to reported content.
