# Accessibility evidence and release gate

Last reviewed 1 November 2026. Work starts at `fc08741b`. This is a development audit, not a certification or a declaration of App Store label eligibility. No accessibility metadata or website has been published.

## Criteria and scope

Apple requires every common task to work with a feature before claiming its label, separately for each supported device. Common tasks include first launch, third-party sign-in, purchases, settings, widgets, and notification actions. Read the [overview](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/overview-of-accessibility-nutrition-labels) before changing the answers below.

The baseline has 1,312 app Swift files, 411 using accessibility APIs, five tabs, and ten implemented games. Source inspection found existing semantics, local-first data, private nickname resolution, hidden-answer rules, Reduce Motion paths, adaptive paywalls and game accessibility layers. These are starting evidence, not completed usability tests.

The quality goal exceeds label eligibility. It includes comfortable AX5 layouts, 44-point custom targets, visible native gesture alternatives, efficient heading and board navigation, stable focus during live changes, and meaningful accessible creation. Labels and automated audits do not establish legal compliance.

Durable drafts and correction of descriptions after sharing are also release-quality goals. Apple does not list them as separate label requirements. The classifications below identify common-task barriers and missing evidence; they do not turn every improvement in this report into an Apple criterion.

## Findings from simulator audits

At 2217 the API returned 18 contrast, ten clipping, six Dynamic Type, two hit-region and one description issue. The [node index](../.audit/accessibility/ui-2217/issues.tsv) and [original descriptions](../.audit/accessibility/ui-2217/issue-details.txt) retain unavailable elements too. At 2238 drawing still had two hit-region findings and Welcome had contrast, clipping and Dynamic Type findings. Native 44-point toolbar targets, shared button wrapping and scrolling Welcome/sign-in layouts changed afterwards and await the final run.

The disabled Send crop measured 1.166:1 before the fix. Opaque semantic roles replaced its blanket opacity. The answer, memory detail, Norwegian AX5 memory editor, privacy and Norwegian AX5 settings audits passed at 2217. Home/Questions countdown, prompt, streak and distance layouts have since changed; the next audit must assess their actual nodes.

Selected old crops measured minimum flat glyph-core/background contrast of 8.174:1 for the AX5 paywall paragraph, 10.664:1 for the native tab bar and 7.377:1 for Back. The [measurement limits](../.audit/accessibility/ui-2156/crop-contrast-notes.txt) exclude thin glyphs, dark glyphs, selection boundaries and other nodes/states. This evidence does not waive a whole audit or establish the contrast label. No provider sheet has been tested.

## Task-by-feature matrix

Every row requires separate iPhone and iPad results. No row is a manual pass until its completed journey and build are recorded.

For every row exercise applicable empty, loading, offline, failure, disabled, completed, and interrupted states, plus the ordinary ready state. Record an inapplicable state with a reason. Check both English and Norwegian, long names, AX5, Bold Text, Reduce Motion, Increase Contrast plus Reduce Transparency, and grayscale. Test focus after presentations, errors, updates, and dismissal. Never expose locked answers, hidden targets, unfinished creature parts, or a partner's private nickname source.

## Usability protocol, pending

Recruit people who regularly use VoiceOver and Voice Control, and people using large text, Switch Control or keyboard access. Include iPhone and iPad users and both supported languages. Agree compensation, recording consent and an accessible stop method. Use synthetic couple data, not participants' private conversations.

Give tasks in plain language without naming the control or gesture. Ask participants to start a space, join it, answer and reveal a question, exchange described photos and transcribed voice, make and edit a drawing, play each game, inspect a shared place, change privacy settings, export data and leave safely. Include an offline interruption, a failed send and a permission refusal. Test third-party sign-in and sandbox purchase cancellation/restoration without a real charge.

Record whether each task was completed independently, where help was needed, focus loss, missed state, wrong actions, hidden information, fatigue and recovery. Ask what was confusing and what they expected. Do not treat speed as the primary measure. Fix blockers, repeat the affected tasks, and leave validation pending until that repeat occurs.

## Documentation differences found

The old design accessibility guide limited transcription to future scope and asked for a VoiceOver smoke pass. This task explicitly expands that scope and requires complete participation and device-specific evidence. The report and release gate replace that readiness claim. The marketing contract refers to `public/screens/`, while current assets live in `marketing/static/screens/`; this work follows the existing static SvelteKit structure.
